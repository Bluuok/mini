## 2. MiniCode：替换建议

### 更清楚的项目定位

`研发资料协作 Agent｜基于 MiniCode 的［实际二开／复现］`

简介：`面向［真实使用者或演示场景］，通过工具调用完成目录搜索、资料读取、摘要生成与经授权的文件修改。`

只有当它真的属于实习工作时，才改写为单位中的研发资料助手；场景设计本身不证明公司实际使用。

### 可选贡献条目

**确实新增／改过文件工具时：**

> 为［具体资料任务］实现［真实工具名］，在执行前校验参数和［实际路径规则］，按字符范围返回文件内容；通过［非法参数／边界输入］用例验证拒绝行为。

避免把“返回内容分段”写成“底层流式读文件”。若沿用上游工具，仅完成配置与场景接入，就把动词改为“配置／接入”，并说清自己的修改。

**确实实现／修改审批链路时：**

> 在［实际写入路径］加入 diff 预览与授权检查，按［实际审批范围］执行写入；使用批准、拒绝及［已覆盖的冲突情况］验证文件最终状态。

不写“所有写入每次必经确认”，除非全部入口与授权策略确实支持该保证。

**确实做过恢复模块时：**

> 将［真实事件种类］写入 JSONL，支持加载历史会话与创建探索分支；通过［对应保存／加载／fork 用例］检查上下文重建。外部文件副作用按实际状态处理。

**确实给主入口接入预算时：**

> 为主 Agent 入口配置［模型轮次／超时／成本中的实际限制］，触顶返回可诊断状态，并通过［真实用例］验证终止行为。

参考代码仅有可选 `maxSteps` 不足以采用这一条；应展示真正传参的位置。

### 90 秒故事模板

“我在［真实背景］处理［一类具体资料任务］，负责［一个模块］。原来的问题是［实际输入与失败现象］。我把［具体操作］接入 Agent 的工具执行链，在执行前做［已实现检查］，写入时按［实际策略］处理确认。选择这个方案，是因为［需求限制］；我考虑过［实际比较过的方案］，但它会带来［具体代价］。我用［日志／用例］检查了［结果］。目前它保证［有限结论］，像［副作用恢复／大文件内存／符号链接等真实未覆盖项］还没有覆盖。”

不要把所有五个 R 点塞进这段话。面试官感兴趣后，再展开一个机制。

### 六个必须准备的追问

| 追问 | 合格回答应含什么 |
|---|---|
| 模型 JSON Schema 与 Zod 为什么都存在？ | 生成约束与执行校验的职责；当前同步方式；漂移怎么办 |
| maxSteps 到底限制什么？谁传参？ | 实际入口、计数单位、一轮多个工具、触顶返回；未启用就承认 |
| read_file 限制了什么？ | 输出长度与底层文件读取的区别；字符／字节／行的单位 |
| 用户拒绝写入后会怎样？ | 工具返回、模型如何继续、文件未变的验证；授权可否复用 |
| 恢复会话会重做写入吗？ | 日志重建与副作用分开；重复、损坏日志和中断边界 |
| 哪些是你写的？ | 一个具体 diff、对应需求和回归；上游循环与工具不冒领 |

## 3. Craft：替换建议

### 更清楚的项目定位

`多后端 Agent 工作台｜基于 Craft Agents 的［实际改动方向］`

保留“深度研究”场景时，需要能展示一条真实研究任务输入和产出；只有 UI 与协议验证时，称为“Agent 工作台”更稳妥，暂不声称研究质量提升。

### 可选贡献条目

**做过后端适配时：**

> 基于现有 AgentBackend 接口接入［实际后端］，映射［文本流／工具事件／取消／错误中实际覆盖的能力］，以［契约用例］验证行为，列明与［另一后端］的功能差异。

**做过事件或 UI 错误处理时：**

> 为［真实失败类型］补充后端到 UI 的结构化事件映射，区分［实际状态］并提供［真实恢复动作］；通过［事件序列／端到端用例］验证错误显示与终止行为。

**做过 Source 接入时：**

> 在现有 Source 接入链路中新增［数据源／认证方式］，由凭据管理模块提供材料，适配层完成［请求组装／工具描述转换］；验证［缺失凭据、超时或失败分支］。

只有真实修改了共享传输或 Session 目录策略，才增加这些条目。使用上游封装本身不等于设计整个统一层。

### 四处危险原句的替换

| 原句方向 | 建议表达 |
|---|---|
| “凭据永远只在宿主进程” | “Source 工具调用与模型后端认证分开处理；初始化消息在存在凭据时会传入 Pi 子进程，具体作用域按部署实现说明。” |
| “sanitize 拒绝路径穿越” | “validateSessionId 用于拒绝非法 ID；sanitizeSessionId 提取路径末段。我的调用链在［实际位置］做校验。” |
| “每个 Session 就是独立工作目录” | “Session 存储与工具工作目录分别管理；工具 cwd 的实际选择为［真实配置／fallback］。” |
| “换模型只改配置” | “对已实现适配器且覆盖的公共能力，可通过配置切换；［不一致能力］需单独处理。” |

### 90 秒故事模板

“我基于 Craft Agents 做［真实场景］，负责［一个适配／事件模块］。接入［实际后端］时，遇到［真实差异或失败］。我在［真实接口位置］做了［映射／错误处理］，让上层能稳定收到［实际契约］。我没有把所有后端能力硬塞成完全一样，而是明确了［能力差异］。验证时使用［实际两组输入或事件轨迹］，检查［成功与失败结果］。当前仍有［未支持能力］，凭据、Session 存储和工具目录的边界也分别定义。”

上述表达中的方案与事件都需要真实经历；没有发生过，就先用它作为实现和验证提纲。

### 六个必须准备的追问

| 追问 | 合格回答应含什么 |
|---|---|
| chat 接口统一后，后端还有哪些差异？ | 工具、流式、取消、历史、错误和鉴权的实际矩阵 |
| Pi 子进程拿到什么凭据？ | Source 与模型凭据区别；传递通道、使用位置与日志脱敏 |

`自托管 Agent 服务｜基于 HappyClaw 的［任务调度／渠道接入等实际方向］`

“跨境电商”只有在你实际准备了巡检、库存等输入和处理流程时才保留；若只是演示场景，直接标明。不要暗示真实商家、线上订单或客户规模。

### 可选贡献条目

**确实做过调度模块时：**

> 为［实际定时任务］实现 occurrence 去重与条件认领，使用［真实事务／lease 方案］处理［已覆盖的竞争或恢复情况］；通过［实际故障用例］验证任务状态，外部副作用保证限定为［真实范围］。

**确实做过渠道适配时：**

**确实做过认证／权限改动时：**

## 5. 三项目联动怎么讲

当前联动文档本来就强调三个项目非同源、只连接能力成长。建议保留这个原则，按真实时间和经历选用下述结构：

“我的项目关注三类问题：工具调用怎样变成可控执行，模型能力怎样接进应用，以及任务怎样在后台稳定运行。［第一个真实项目］里我负责［实际贡献］；后续在［第二项目］补了［不同能力］。这几个项目的代码来源和使用场景各不相同，我能具体展示的是［一到两个模块与验证］。”

没有真实时间顺序时，不要加“因此上线后团队又让我……”之类因果。资料中的 R01/R08 等编号只服务内部准备，面试直接说机制名称。

可以主动控制讲述范围，但面试官追问实际存在的 MCP、命令执行、权限对象或子代理时，要按实际版本回答。把这些词列为“不主动展开”不等于它们不存在。

## 6. 如何回答 AI 辅助和个人贡献

可采用的结构：

“这个模块基于［上游版本］，已有［现有能力］。我负责［真实改动］。AI 帮助我［实际使用方式］，我自己核对了［关键逻辑］并通过［真实测试］确认行为。［某项上游能力］不是我写的；我能解释它和自己模块的接口。”

这比泛称“独立从零实现整个系统”更便于展示贡献。能否不用 AI 独立改一个小功能、调试一次故障、解释一段异步流程，比背完架构名词更容易检验当前熟练程度。

## 7. 面试前五个完成节点

1. **事实卡完成：**确认毕业与到岗信息、实习归属、每个项目的真实状态和实际日期。
2. **贡献卡完成：**选一个本人模块，能打开对应代码、diff 和需求；若只是复现，清楚标明复现。
3. **演示完成：**一次成功路径、一次拒绝／失败路径、一次恢复或边界；演示使用可公开或脱敏输入。
4. **解释完成：**口述 90 秒故事，并接住表格中的追问；不知道的部分写在限制里。
5. **投递检查完成：**按目标 JD 选版本，检查 PDF 全页与链接，确保数字和措辞与证据卡一致。

如果时间紧，优先完成一个主项目的这五项。第三项目可以晚些再上简历；不要为了凑齐三个名字让整份简历承担无法证明的范围。
