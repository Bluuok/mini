## 1. 总体判断

这组项目有适合 Agent 应用工程实习岗的题材：工具执行闭环、写入审批、会话状态、模型适配、流式事件与后台调度。材料已经能够描述“用户为什么需要它、工程上有哪些难点”。最值得保留的是对执行可控性和失败处理的关注。

目前材料尚未形成可以直接投递、能经受连续追问的完整履历。最主要的问题有四个：个人贡献与上游能力没有充分分开；简历中的实现主张缺少提交与实测证据；项目故事过长且重复承担平台级职责；简历存在实际打印分页故障。

这是对当前材料的判断，不等于对本人能力的最终评价。当前无法核实你的独立编码能力、学校背景、真实实习情况、已做但未收录的修改，也无法据此给出录用概率或可靠的竞争力分数。若个人信息占位是为了评审脱敏，不据此扣能力分；实际投递版仍须补全。

**建议的投递主线：能够在现有 Agent 项目中独立完成一个可验收的功能模块，并说明实现、失败处理、测试和取舍的应用工程实习生。**

## 4. 简历具体怎么改

### 4.1 身份与经历

建议标题为“Agent 应用开发实习生”；毕业求职时另出“Agent 应用开发工程师（应届）”版本。实习与应届招聘的资格条件可能不同，应使用真实毕业时间匹配岗位。

头部优先放姓名、联系方式、毕业年月、求职城市、到岗信息和作品入口。照片、出生年月、完整课程列表的优先级较低；具体招聘系统要求提交时再按要求填写。GPA、排名、英语只写真实且有助于判断的内容，不需要为填满版面而添加。

如果没有真实实习，直接用“项目经历”。有真实实习则先讲该单位、部门场景和本人交付，再列个人项目。不能用一个开源项目的完整能力列表替代在公司的实际职责。

### 4.2 信息结构

对当前这组应届／实习材料，建议先做一页主投版；两页不是禁忌，但必须有足够独立、可核查的内容支撑。

建议顺序：基本信息与可用性 → 教育 → 4–6 行技能 → 最强实际经历／项目 → 第二项目 → 可选补充成果。真实且相关的实习可以提前。

主项目保留 3 条，第二项目 2–3 条；每条尽量 1–2 行。删掉重复的抽象设计语句，把机制细节留到项目 README 和面试材料。优先删内容，避免为了塞下一页持续缩小字号。

### 4.3 技能部分

当前技能与项目重复，且“掌握”“完整开发”“理解方法论边界”不便验证。改为技能加应用场景：

- TypeScript/Node.js：异步工具调度、文件操作、事件流、异常处理；只保留实际能写和调试的部分。
- Agent 工程：Tool Calling、参数校验、执行步数限制、会话持久化；分别关联项目证据。
- Web/工程工具：React、HTTP/WebSocket、SQLite、Git、Docker；区分独立实现、使用过和仅阅读。
- 补充能力：Python、RAG、LangGraph 等仅在实际做过后加入，不把 JD 名词复制为技能。

数据结构、算法、网络、操作系统和数据库基础应进入面试准备，而不一定变成长串简历关键词。

另有一处需要本人校准的历史口径：`我的方案I学习文档.md:3–9` 曾自述“TypeScript 不熟、有 Java 基础”，当前简历则写“熟练使用 TypeScript/Node.js”。旧学习笔记可能已经过时，不能据此判断当前水平；建议用“能否独立写一个异步工具、定位错误、补一个回归测试”检验现在是否撑得住“熟练”。不必为了简历上的形容词硬扛超出能力范围的追问。

### 4.4 实际排版检查

检查条件：Windows，Edge 153 的 Chromium 打印引擎，本地 HTML，A4，使用原 CSS 页面尺寸，外部网络被阻止，脚本禁用。本次 PDF 实际大小 280,052 字节。

## 5. MiniCode：最适合建立一条可核查的工程主线

### 保留什么

基准把场景限定为项目资料目录中的多步文档协作，明确不把它称为 RAG 或通用 Coding Agent（基准 21–26 行）。固定链路是工具调用、结果回填、diff、人工确认、写入以及会话记录（30–45 行）。这个边界对实习生项目有利：可以用少量输入和断言展示完整闭环。

工具的模型侧 Schema 与执行侧运行时校验、受控文件访问、写前确认，适合作为主要技术点。源码取证能定位到执行循环、Zod 校验、diff 审阅和 JSONL 会话函数；这证明代码包里存在对应实现，仍不能证明全部由你编写。

**特别需要对齐参考项目与自己的产品：**参考仓库 `README.md:20–28` 把 MiniCode 定位为终端 Coding 工具，`src/tools/index.ts:51–88` 注册了命令执行、Web、Skill、MCP 等广泛能力；你的基准文档则限定为研发资料协作。这个差异可以是合理的场景化二开，但应提交实际删减／禁用／新增的工具与权限配置证据。仅改变文档名称还不能证明完成场景改造。基准中的 `search_files/apply_diff` 与参考源码的 `grep_files/edit_file/patch_file` 也并非直接同名，应建立真实工具映射。

### 需要收紧的表述

1. **JSON Schema 不自动等于唯一事实源。** 定稿 50–52 行明确两份定义当前靠封装维护，自动生成仍属于改进方向。简历可以写“模型侧参数描述与运行时校验”，不能声称已经从单一 Schema 自动派生全部契约。
2. **maxSteps 在参考主入口并未默认启用。** `src/agent-loop.ts:113–133,176` 将它定义为可选参数，循环条件允许未传值时持续迭代；`src/index.ts:253–266` 调用时未传入。`src/agents/manager.ts:132–139` 的子代理才传入限制。因此简历 78 行和定稿 52、61 行的终止保护需要真实产品版本支持。该变量计模型请求轮次，一轮可有多个工具调用，也不宜说成严格限制工具调用总次数。启用上限仍不保证任务成功。
3. **恢复会话和恢复副作用不同。** JSONL 可以支持历史重建；文件是否已写入、重试会否重复、写入中途失败如何处理需要单独说明。定稿 75–84 行已经承认文件最终状态以实际写入为准，应把这个边界保留下来。
4. **“写前确认”必须限定触发条件。** `file-review.ts:60–65` 在传入权限管理器时才调用审批；`permissions.ts:421–427` 还允许已授权范围复用批准。TTY 路径会传入权限管理器，但不能概括为所有调用路径、每一次写入均重新弹窗。必须能演示拒绝确认后不落盘；一次被批准的 diff 是否绑定随后写入的内容，也属于追问范围。
5. **受控输出、文件 I/O 与目录隔离分别说明。** 学习文档 59 行写“2000 行／单行 2000 字符”，参考 `read-file.ts:12–18,33–55` 实际默认 8,000 字符、上限 20,000 字符，先完整读文件再截取；这能控制返回模型的内容量，不能据此证明底层是流式分页或大文件内存受控。`workspace.ts:9–27` 的路径归一化与相对路径检查，也不能自动证明符号链接等边界已覆盖。

### 推荐故事核心

选择一次具体失败：例如多步文档任务中的错误参数、拒绝写入或恢复历史会话。按“输入是什么 → 原来如何失败 → 我改了哪一段 → 如何验证 → 哪些情况仍不保证”讲完整。本人没有改过核心循环时，完全可以围绕一个实际新增工具、一个 bug 修复或一组失败回归来讲。

**最小证据包建议：**一个可公开的小型资料目录、一次成功读写轨迹、一次非法参数拒绝、一次人工拒绝写入、一次历史恢复记录、对应本人提交。测试用例是建议补做的内容，本次没有运行这些业务测试。

## 6. Craft：保留架构理解，补上接口与隔离边界

### 价值与取舍

Craft 可以展示 TypeScript 抽象、前后端调用链和模型适配能力。相比单纯调用模型 API，区分业务状态、传输协议和事件类型有实质价值。建议从多后端适配或流式错误处理里选一条本人完成的链路；“五个方向全部个人自研”的证据成本明显更高。

故事 22–27、50–54 行将五项能力及测试写为本人事实，54、200–205 行包含“已知结果”“tsc 全仓 strict + CI”等验证承诺。复现文档 3、7–8 行却明确 `✅` 只表示参考源码已核实，`🔧` 表示自行设计；326–327 行的测试属于待满足的验收条件。应把参考源码事实、施工规格和个人已完成产出分栏。当前未找到本人运行结果，不把“测试全绿”视为成立，也不据此断言你在别处一定没做过。

### 必须对齐源码的几个点

| 原文或潜在印象 | 参考源码证据 | 推荐准确口径 |

## 7. HappyClaw：题材有深度，保证范围需要重新划清

### 价值与取舍

定时任务、消息入口与工作区权限是有工程含量的切入点。对平台实习岗，一条“重复触发 → 任务物化 → 竞争认领 → 结果状态”的可靠性故事，足以展现数据库、并发和恢复思考。七渠道、角色治理、认证和调度同时作为个人完整自研主张，反而需要非常宽的证据支持。

参考目录的 `package.json:70–78` 指向 `riba2534/happyclaw`；当前指定目录未见可用的本人 Git 历史。复现文档 3–7 行也明确把参考仓库作为机制查证材料。故事 50、54、61 行的“全部自研模块”“Vitest+CI”“已实现”应优先核对。现有证据足以要求澄清，尚不足以断言你没有在别处完成实现。

### 三个必须修正的具体口径

**任务认领不是文档所说的无事务单语句。** 复现文档 179–187 行的描述与参考 `src/db.ts:5351–5381` 不一致：代码在事务中先选候选，再条件更新，使用受影响行数判断认领成功。两种实现可以各有讨论，但面试要对自己实际版本负责。复现文档 192 行自定的 10 分钟 lease，与调度器参考默认 60 秒也应明确区分。

**“宁可错过，不可重复”要限定到具体状态与路径。** 故事 421 行用了这一绝对表述，同时承认没有实际启动多实例演示。参考 `db.ts:5411–5457` 把已启动但过期的任务标为失败、不复活，能说明一种保守恢复策略；它本身不证明所有外部 API、进程或消息副作用均不会重复。token 的条件检查保护其参与的状态更新，若下游不校验 token，也没有幂等键，则不能自动阻止旧 worker 已经发出的动作。未实际做多实例故障测试时应说“源码分析／设计目标”，不能写成亲自验证的线上保证。

**Owner 拒绝执行不等于零回执。** 定稿 160–162、191–193 行及故事 189、192 行强调“不回执／静默拒”；参考 `im-command-utils.ts:282–313` 会返回拒绝原因，`index.ts:3552–3592` 将失败原因组织为回复。应精确写是哪一种入口、命令和拒绝策略，不能把全部 Owner Gate 描述成静默。

### 另外两项边界

故事 157、226–230 行把七渠道、两个真连适配器与五个骨架测试写成第一人称；复现文档 235 行却说明参考仓库没有字面 `IMChannel` 接口，`ImChannelAdapter` 是拟议设计。若你实现了自有接口，应展示实际代码和契约测试；不能只引用上游的多渠道支持证明自己的接口已经完成。

认证源码确实有随机 token、HMAC、签名长度检查、常量时间比较、Cookie 属性和限流。但 HTTPS 下才使用 Secure；当前限流在内存 Map 中，不能默认当作多个服务实例共享的全局限流。简历应讲自己实际实现／改过的环节及部署条件。HMAC、权限授权、CSRF 条件和爆破限流是不同问题，不宜合成“后台完全安全”的结论。

### 推荐保留的主故事

如果你实际改过调度模块，就讲一个重复触发或崩溃恢复案例，并说明选择“允许漏一次”还是“允许重试”、为什么业务能接受，以及测试覆盖了哪一层。如果你实际贡献在渠道适配，就围绕一个渠道的消息规范化、身份映射和错误处理深讲，不必主动背完整调度器。
