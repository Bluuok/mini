# 改进 PR 提案

目标：中国 Agent 应用开发应届／实习岗位。这里的 PR 是可拆分执行的本地修改提案，尚未创建分支、提交或 GitHub Pull Request。所有“验收”均为后续执行条件，不表示本次已经完成。

当前目录不是 Git 仓库。应先确认真正属于你的实现仓库；不要把参考源码快照当作个人贡献提交，也不要为了产生 Git 历史去制造虚假的开发时间线。

## PR-01 · 校准经历归属与个人贡献口径

**优先级：P0。类型：事实整理与文档修订。依赖：本人事实确认。**

**问题与变化：**当前 MiniCode 对应场景出现在实习经历，三个项目使用大量“设计／实现”表达，但个人信息、公司、时间和贡献记录尚无法对应。修改后，每条对外主张都能区分上游已有、本人使用、本人新增与实测结果。

**涉及文件：**`简历-AI应用开发.html:58–83`、`待办清单.md:25–41`、三个 `*-定稿.md`；建议新增 `项目证据/贡献台账.md`。这张台账应进入本人真实项目仓库，而非继续只放参考资料目录。

**具体改动：**

1. 填写真正的教育、毕业年月与实习可用性；评审脱敏版可以继续匿名。
2. 明确 MiniCode 场景是否真实发生在公司。真实实习写单位、部门场景和本人模块；个人实践改列开源二开／个人项目。
3. 每项目记录上游仓库与固定版本、本人改动文件／提交、完成日期、验证命令／结果、未完成项。
4. 把文档中的“完成状态”改为明确标签：已阅读、已复现、本人已改、已测试、已部署。允许一个模块同时有多个标签，不混为一个“已完成”。

**示例替换：**

原：`设计了统一能力接入层，实现了外部研究能力的统一接入与调用。`

本人只读过源码时：`梳理 Craft Agents 的外部能力接入链路，理解凭据、工具描述与调用转换的分工。` 此类内容通常放学习记录，简历仅在有可展示产出时保留。

本人实际新增适配器时：`基于 Craft Agents 为［实际数据源］新增适配器，完成［实际字段／异常］映射，并用［对应契约用例］验证接入行为。`

**验收：**每条“实现／设计／优化／支持”都能指向本人产出；实际投递版无身份占位；没有真实实习的项目不放“实习经历”；保留可证明的作者与上游信息。

## PR-02 · 统一 MiniCode 的产品边界与执行语义

**优先级：P0。类型：先修正文档，缺少实现时另立代码任务。依赖：PR-01。**

**问题与变化：**研发资料协作定稿与通用 Coding 工具参考仓库不是同一个已确认产品。修改后，用真实工具清单描述实际产品，并明确 Schema、审批、恢复的能力边界。

**涉及文件：**`MiniCode-项目定义-基准.md:21–45,60–71`、`MiniCode-定稿.md:21–29,50–52,75–84`、简历 MiniCode 条目。取证参考：`minicode付费版内参/MiniCode-main/src/tools/index.ts:51–88`、`src/tool.ts:27–33,102–130`、`src/file-review.ts:46–69`、`src/session.ts`。

**具体改动：**

1. 新增“参考能力 → 产品启用能力 → 本人改动”表。说明 `run_command`、Web、MCP、Skill 是否实际暴露；写“受控文件工具”时限定控制对象。
2. 对齐 `search_files/apply_diff` 与真实工具名；简历用“搜索／补丁写入”等概念词，面试仅使用本人真实仓库／实际产品版本中的符号。参考快照的命名不能证明本人已实现。
3. Schema 改为“模型侧参数描述 + 执行侧运行时校验”；若未实现自动派生，不使用“单一事实源自动生成”。
4. 把恢复分为会话历史重建、任务续做和外部副作用恢复；逐项说明已支持与未支持。
5. 审批说明绑定哪一个操作、由谁确认、拒绝后如何返回、文件在确认后发生变化怎么办；没有做的条件写入限制。
6. 修正 `maxSteps` 口径：参考 `src/index.ts:253–266` 未传该可选参数，子代理入口才启用；若本人产品确实设置了上限，给出该调用位置。按模型轮次说明计数，不能泛称工具调用次数上限。
7. 修正读取边界：参考实现按字符截取输出，先完整 `readFile`，并非流式文件分页；学习文档中的“2000行”与参考默认8,000／上限20,000字符不同。按本人版本记录。

**验收：**工具映射与运行时一致；给出一次允许写入和一次拒绝写入的日志；会话恢复演示不被用来证明文件副作用可回滚；`maxSteps` 触顶能说明终止原因，且不宣称保证成功。

如产品未启用 `maxSteps`，删去“已具有最大步数保护”即可先完成口径修订；若决定补实现，另验证主入口实际传参和触顶行为。本 PR 不把“存在可选参数”当成已完成接线。

**建议测试，不是本次结果：**非法参数拒绝执行、目录外路径、符号链接边界、拒绝确认文件哈希不变、批准后文件变化冲突、恢复日志末行不完整。优先选择本人声明涉及的边界测试。

## PR-03 · 修复简历打印与缩短主投版本

**优先级：P0。类型：简历 HTML/CSS 与文字编辑。依赖：事实口径确认；纯分页问题可单独修。**

**问题与变化：**原稿打印为 4 页，其中有空白页和只有一条技能的孤页。修改后形成信息分配合理、可打印、可提取文本的主投版。

**涉及文件：**`简历-AI应用开发.html:1,19–20,38–39,54–125`。原样张及测量记录位于本目录 `qa/`。

**修复步骤：**

1. 删除 doctype 后多余的 `/`。这是确定的字符错误；不要声称单独删除就能修复所有分页。
2. 先选排版策略：主投版推荐一个连续文档容器、A4 页边距和自然分页；若保留手动两页，就对每页高度与内容做明确验收。避免 `min-height:297mm`、文档前置文字和强制分页叠加后仍无溢出检测。
3. 使用一致的打印盒模型，打印时清除屏幕页间距、阴影和无关装饰。项目标题与其第一条内容避免分离；不要把一整个长项目永久设为不可分页，反而推到后页。
4. 将简历收敛为两个详细项目、每个 2–3 条；第三个用一行或留作品集。先删冗余，字号建议从正文 10.5–11pt 起试，按打印可读性调整。
5. 增加可点击的仓库／演示入口。手机分享版可单独设置 `width:min(210mm,100%)` 等屏幕样式；打印样式与屏幕样式分开。

**验收：**

- A4、100% 缩放、无浏览器页眉页脚时，没有空白页、截断和孤立末条。
- 若目标一页则实际输出一页；若因真实经历需要两页，第二页有足够实质内容。
- PDF 全页肉眼检查通过；姓名、学校、项目顺序和中文均能按预期提取；链接可点击。
- 390px 网页若作为分享入口则无非预期横向滚动；若仅作打印编辑器，明确其用途。

**回退：**另存简历投递版，保留原稿和原始样张。本提案没有替你补写个人信息，也没有生成冒充定稿的新履历。

## PR-04 · 把 Craft 收敛成一项本人可证明的适配／事件贡献

**优先级：P1；其中与源码冲突的确定事实应按 P0 修。类型：项目故事与证据修订。依赖：PR-01。**

**问题与变化：**“多模型、多端、统一能力、Session、统一错误恢复”同时铺开，容易让面试官理解为你设计了完整上游平台。修改后用一个具体能力证明设计和排障能力。

**涉及文件：**简历 Craft 部分、`Craft-定稿.md`、`Craft-故事.md`、`Craft-复现文档.md`。优先选以下一个真实发生的模块：一个后端适配器、一种结构化事件、一条前后端错误恢复链路，或一组契约回归。

**具体改动：**

1. 画一条实际调用链：UI 操作 → RPC／传输 → Session → 后端适配 → 事件 → UI；标出本人修改节点。
2. 给后端能力建矩阵：流式输出、工具调用、取消、历史格式、权限请求和错误类型。把“只改配置即可切换”限定到已适配、已验证的公共能力集合。
3. Session/Workspace 描述限定为应用状态／工作区边界；需要进程或系统级隔离时另列机制和验证。
4. 为事件契约说明重复、乱序、取消后晚到事件和终止事件的行为；不因统一为一个联合类型就宣称所有错误都可恢复。
5. 删除无法定位本人产出的宏大条目，保留一个输入、一个处理策略、一个结果。

**本次已取证的 P0 纠错：**

- 定稿 113 行／复现 186–191 行的“凭据永远只在宿主”，改为分清 Source 凭据和模型凭据。`pi-agent.ts:543–560` 的初始化消息在存在凭据时向 Pi 子进程传 `apiKey/piAuth`；不能保留全称断言。
- 复现 206 行／故事 171、174 行的 `sanitizeSessionId`“拒绝路径穿越”，改为 `validateSessionId` 抛错、sanitize 取 basename，并核对真实调用链。
- 复现 201 行的默认工作目录，分清 Session 存储目录、`sdkCwd` 和工具 `workingDirectory`，不能用前者证明后者隔离。
- 故事 384–387 行／复现 253 行区分 `AgentError` 与 wire 事件 `TypedError`；复现 188 行把三条指令改称协议子集；66 行按该段列出的 3 个 packages 与 2 个 apps 修正为五个组件，并说明是裁剪范围。
- 故事 54、200–205 行的 strict/CI/测试结果仅在拿到本人运行记录时保留；复现规格里的 DoD 不充当实测结果。

**验收：**两种已声明后端或两种已声明传输用同一组有意义的契约用例验证；失败结果能映射到具体日志与 UI 行为；没有把类型检查通过写成研究任务质量提升。

**建议替换结构：**`基于 Craft Agents 的［现有接口］，为［具体后端／事件］实现［本人改动］，处理［一种真实失败］；在［版本、范围］下通过［验收］，当前不覆盖［限制］。`

## PR-05 · 校正 HappyClaw 的租约、权限与恢复承诺

**优先级：P0（口径）；P1（补充实现与验证）。类型：文档纠错 + 有边界的可靠性任务。依赖：PR-01。**

**问题与变化：**复现文档对任务认领的事务描述与参考源码不同；调度互斥、身份授权和结果不重复容易被讲成同一种保证。修改后每个承诺分别对应状态、不变量和故障测试。

**涉及文件：**`HappyClaw-复现文档.md:179–192`、`HappyClaw-定稿.md`、`HappyClaw-故事.md`、简历 HappyClaw 部分。参考源码 `happyclaw付费版内参/happyclaw-main/src/db.ts:5220–5285,5351–5381,5411–5495` 和 `src/task-scheduler.ts:2129,2270–2297,3204–3342`。

**确定的文档修正：**

原：任务认领是“单条语句”，因此“无需额外事务”。

建议：`参考版本在事务内选择候选任务，再通过带状态／租约条件的 UPDATE 竞争认领，以更新行数判断是否成功。若自行改写成另一实现，应单独说明该实现与验证结果。`

复现参数和源码默认值分开写：复现文档给出的 10 分钟租约属于自行选取的参数；参考调度源码当前为 60 秒。不要混为“原项目就是这么配置”。

**逐层说明保证：**

1. occurrence key：同一计划发生点是否重复物化。
2. claim：多个 worker 是否同时认领同一行。
3. lease/owner/token：谁仍有权续租或更新状态。
4. effect：已启动进程、外部 API 或消息是否可被旧 worker 继续执行。
5. notification：业务已完成但回执失败时如何处理。

数据库条件更新只能直接证明它保护的状态写入；外部副作用要看幂等键、去重记录、下游栅栏或补偿策略。不能从“有 lease_token”直接推导端到端 exactly-once。

**权限与认证口径：**区分管理角色、工作区所有者、IM 绑定身份和会话认证。说明拒绝的是动作还是消息回执。HMAC 保护签名完整性；Cookie 的 HttpOnly/SameSite/Secure 条件、会话存储与限流作用域仍须分别解释。

确定的回执冲突也要修：定稿 160–162、191–193 行的“静默拒”不覆盖参考 `im-command-utils.ts:282–313` 与 `index.ts:3552–3592` 的所有命令路径，后者会返回失败原因。故事 50、54、61 行的“个人独立开发／Vitest+CI／已实现”，必须有本人实现与实际测试记录后才能保留。

**建议故障验收：**同一 occurrence 重复提交；两个 worker 竞争；认领后退出；启动后 lease 过期；旧 token 写回；外部 API 已成功但完成状态未提交；IM 非 Owner 调用；同名用户从多个来源尝试。只保留确实实现和有结果的案例进入简历。

**接受的降级结果：**若未实现业务幂等，可以明确写“覆盖 occurrence 去重和数据库任务状态竞争；外部副作用去重尚未覆盖”。诚实限定可以完成这份文档 PR，无需先重写整套调度系统。

## PR-06 · 建立可复现证据与小型评测集

**优先级：P1。类型：证据产物／针对性测试。依赖：选定主项目与本人仓库。**

**问题与变化：**现有材料大量使用定性结论，缺少统一结果入口。修改后，面试官能从一个 README 重现主要功能与关键失败。

**建议新增：**`evidence/README.md`、脱敏 fixtures、运行配置模板、实际运行记录、失败样例、模块测试及评测脚本。不得存放密钥或私人业务数据。

**每项结果记录：**项目／上游／本人提交版本、模型与参数、输入样例、命令、预期结果、实际结果、时间、限制。日志记录运行 ID，便于对应代码与报告。

| 目标 | 建议度量 | 避免的误用 |
|---|---|---|
| 多步任务能否完成 | 成功任务数／有效样本数；失败分类 | 把一次演示当总体完成率 |
| 改动是否更稳 | 相同数据与设置下的前后对比 | 同时换模型、Prompt 和输入后全部归因代码 |
| 成本与时延 | 每成功任务 token/调用成本；时延分布与重试 | 只算成功且最快的单次调用 |
| 安全拒绝 | 应拒绝样例中的正确拒绝数与误拒绝情况 | 把所有请求都拒绝当作高安全性 |
| 调度可靠性 | 重复认领、重复副作用、漏执行、超时恢复分别统计 | 用“状态没重复”替代“业务没有重复” |

可以先准备约 12–20 个覆盖不同路径的小样例，这只是工作规模建议，不是既有数据，也不是显著性保证。随机性任务做重复运行并报告设置；用于调试的样例与保留验证样例分开。样本很小时优先报告 `x/n` 和失败明细，不给没有依据的漂亮百分比。

**验收：**另一位开发者照 README 能运行核心演示；至少一个改动前后行为差异有证据；所有进入简历的数字均能追溯原始结果。没有测出的数字保留为空，不补造。

## PR-07 · 形成两个有取舍的投递版本

**优先级：P1。类型：简历编辑。依赖：PR-01、主项目证据。**

**版本 A：Agent 应用／工具链。**突出 MiniCode 的实际工具或失败处理贡献；第二项目补接入或服务化。技能以实际语言、工具调用、状态与测试为主。

**版本 B：平台／全栈。**按 JD 选择 Craft 或 HappyClaw 作为主项目；分别强调一条跨端链路或一条可靠性链路，MiniCode 作为补充。

具体岗位强制 Java/Python 时先判断实际能力是否满足，再决定投递与补足；不能仅改技能名字。模型训练／强化学习岗位没有对应实践时，不用现有项目自动生成“算法版”。

**验收：**标题、技能、项目顺序与同一份 JD 一致；每版两条最强证据在前半页可见；不同版本中的事实、时间、贡献和数字一致。

## PR-08 · 把长故事改成可追问的真实事件

**优先级：P1。类型：面试材料。依赖：PR-01、02、04、05 的口径。**

**涉及文件：**三个定稿、Craft/HappyClaw 故事和《三项目联动-步6》。长文保留为知识参考；每项目新增一张一页故事卡。

**故事卡内容：**实际背景、本人负责内容、一次真实失败、采取方案、为何没选另一方案、验证证据、剩余限制。每卡只选择一个主要冲突。

**90 秒结构：**15 秒背景与职责，20 秒具体问题，30 秒改动和取舍，15 秒验证，10 秒限制。时间为练习参考，不要求机械分秒。

**验收：**无需背源码目录也能口述；面试官追问“哪行你改的、为什么、失败后怎样、怎么知道好了”时都能展示或承认边界；没有把三个项目编造成未经证实的同一企业生产系统。

## 建议执行顺序

先做 PR-01 与 PR-03 的明确问题；并行整理 PR-02/04/05 的文档口径。随后只为选定主项目执行 PR-06，再做 PR-07/08。业务代码同一时间保持一个写入者，避免多个修改者在参考快照与真实仓库间相互覆盖。

最终交付标准是“事实一致、贡献清楚、演示可复现、排版可投递”。这些提案不要求把三套上游产品全部重做一遍。
