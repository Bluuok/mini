# /asu：经历酥化

把用户做过的事情翻译成招聘方容易理解、可以继续追问、也能由证据支撑的表达。酥化是岗位定位和证据组织，不是虚构头衔、公司、项目、技术栈或数据。

## 工作流程

1. 先确认目标岗位、岗位描述、求职渠道和用户希望突出的方向。材料不足时先基于已有事实给初稿，并列出最多 5 个关键待补项。
2. 判断经历是否属于三项目（MiniCode / Craft Agents / HappyClaw）。属于则按 `project-router.md` 定位项目 refs 与 codewiki，读 `user-intake.md` 补问缺失的高影响问题；不属于则只基于用户提供的简历、项目说明、作品集、公开仓库或截图。
3. 输出 1—3 个岗位定位，区分稳妥版和进取版；进取版必须说明需要补充的证据。
4. 按“动作 → 系统能力 → 业务价值 → 结果证据 → 个人边界”重写经历和项目要点。
   - 三项目 bullet 保持四段式：`针对[业务问题]，基于[技术]，设计了[工程方案]，实现了[验证效果]。`
   - 每个 bullet 对应一个 R 点，先核对 `resume-points.md` 的 Scope Boundary 再落笔。
5. 生成简历摘要、Boss 直聘/微信 HR 短开场白，以及一版稍完整的自我介绍。
6. 用“原始说法—建议写法—事实证据—个人边界—风险/待确认”审计每个强主张。

## 表达边界

- 正式职位、公司、时间和教育背景保持真实。
- 只有能说明决策、交付和结果时，才使用“主导”“负责人”“Owner”等强动词。
- 没有可靠数字时使用可核验的定性结果，不编造百分比、用户量、延迟或排名。
- 对没有直接负责的内容明确写“团队负责”或“待确认”，不替用户冒领。
- 用户要求制作 HTML/PDF 文件时，转入 `/resume` 或 `/asu-resume` 模式；要求记录投递和 Offer 时，说明本 skill 不包含投递跟踪，引导使用其他工具。
- 用户粘贴 JD/公司背景做场景化对齐时，转入 Scenario Alignment Path（见 SKILL.md Step 1a），先把业务问题槽替换为 JD 场景痛点再输出。
- 用户要求面试 Q&A 预测时，转入 Q&A Prediction Path（见 SKILL.md Step 1b）；要求项目故事/讲清楚项目时，转入 Story Generation Path（见 SKILL.md Step 1c）。
- 用户经历是三项目时，复用项目 refs 里预写的 bullet（已是四段式），仅在用户有领域化表达需求时调整措辞，四段式结构必须保留。
- 掌握程度降级：所选方案/R 点超出用户掌握程度时（如 L2 用户拿到高风险 R 点），警告并提供降级路径，不替用户硬扛。

## 默认输出

除非用户只要其中一项，否则按以下顺序交付：

1. 一句话岗位定位；
2. 简历顶部摘要；
3. 2—4 条项目/经历改写；
4. HR 开场白短版和完整但简洁版；
5. 证据补强清单与可能追问。

Boss 直聘或微信开场白默认控制在约 80—160 字，先说身份和方向，再说一个真实成果，最后邀请继续交流。
