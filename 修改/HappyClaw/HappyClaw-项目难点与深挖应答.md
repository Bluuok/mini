### 先分入口，再讲共用执行

```text
IM：收到消息 → 保留渠道/账号/会话信息 → 准入与资源检查
             → 定位 Session → 执行 → 普通回复

定时：计划到点 → 生成发生点记录 → 条件认领 → 执行 → 记录结果

Profile：创建/局部编辑/内容快照/恢复，是独立配置维护链。
```

跨境电商是运营事项整理的演示场景。输入由用户提供，定时 prompt 是计划中保存的文本；没有业务 Adapter 就不自动取得当天订单或库存。共用执行函数不等于各入口拥有完全相同的 Profile、身份和输出保证。

## 难点一：只改一段配置，为什么其他段也可能被清空？

**面试主问：**“讲一个你在实现过程中处理的具体问题，不用介绍整个项目。”

**证据性质：**当前路由明确记录了默认值与 PATCH 语义风险；有实现及局部更新、快照和恢复的测试定义。没有该问题的个人原始故障日志，因此默认按实现难点讲，而不是宣称发生过配置丢失事故。依据：[Profile 路由][profile-routes]、[Profile 存储][profile-store]、[Profile 测试][profile-tests]。

### 六项复盘：从用户的一次编辑开始

| 项目 | 可以讲清楚的内容 |
|---|---|
| 当时要完成的操作 | 用户只修改数字员工的工具说明，其他三段内容保持不变 |
| 原本预期 | 未提交字段保留原值；明确提交空字符串才表示清空 |
| 实际现象／风险切片 | 创建接口会补空默认值；如果更新链路也补默认值，可能把“原本没提交”变成“提交了空值”。这是当前代码注释与实现所处理的问题，不虚构某次用户损失 |
| 定位到哪一层 | 原始请求、Schema 解析结果、字段转换、存储更新之间，而不是先判断模型行为有问题 |
| 具体调整 | 更新使用无默认值的可选字段，只转发明确提供的键；存储保留其他值，更新前记录内容快照 |
| 调整后的可观察结果 | 只修改一段不影响另外三段；主动清空能生效；恢复旧内容会形成新版本，而不是抹掉之后的历史 |

### 主动介绍：先讲这一段

> 我实现 Profile 时，一个重点是局部修改不能误伤其他配置。比如用户只修改工具说明，请求里没有其他三段，不代表用户想把它们清空。创建接口可以给缺失字段补默认值，但更新接口不能直接沿用这个语义。我把更新字段改成只接收明确提交的内容，没传就保留，传空字符串才清空；修改前保存内容快照，恢复时生成一个新版本。这样局部编辑、主动清空和历史恢复各有明确结果，不会只因为数据类型合法就误解用户的编辑意图。

**主动收口：**“我主要解决的是局部更新语义和历史可回看，不是做了一套完整版本控制系统。”

### 第一层追问：两种请求，结果必须不同

以下是说明行为的输入，不是本轮真实请求记录。假设原四段都有内容。

只修改工具说明：

```json
{"segments":{"tools":"优先使用只读工具"}}
```

预期：`tools` 变为新内容，`identity`、`soul`、`agents` 保持原值。

主动清空工具说明：

```json
{"segments":{"tools":""}}
```

预期：只清空 `tools`，另外三段仍保持原值。没有 `segments` 的请求不应通过默认值把四段全部补成空；本例不讨论额外新增的空请求拒绝规则。

### 五类追问：把定位过程讲具体

**架构问：为什么从请求解析查起，不先查数据库？**

> 因为字段语义可能在到达数据库前就丢了。我会先比较原始请求有没有那个键，再看解析后的对象、转给存储的补丁和最终保存值。原始请求没字段、解析后却有空字符串，问题就在前面的转换；传给存储已经正确、保存后不正确，再看存储更新。这是一条可复现的定位路线。

**实现问：怎么区分没传和空字符串？**

> 不按真假值判断，而是检查是不是 undefined。空字符串也是用户明确提供的合法值，应该往下传；没有字段才保留旧值。否则用一个简单的“有值才更新”判断，又会导致用户无法主动清空。

**取舍问：让前端每次提交四段完整内容不就行了吗？**

> 那可以定义成另一种全量替换接口，但不能代替当前局部更新契约。服务端需要明确知道此次要改什么，不把正确性寄托在每个客户端都补齐字段。当前做法也不等于解决了多人同时编辑覆盖，那个问题需要另行定义版本冲突处理。

**失败问：恢复为什么不是把版本号退回去？**

> 恢复旧内容也是一次新的修改。当前先保留修改前内容，再用旧快照的四段生成新版本，这样能看见曾经发生过哪些变化。这里恢复的是四段文本，不自动恢复所有运行配置，更不能把它说成外部副作用回滚。

**职责问：哪些是你负责的，而不是 SDK 自带的？**

> 我围绕这个选点复现实现了应用层字段、更新转换、内容快照和恢复入口。模型执行循环来自 SDK，但用户编辑配置到持久化这一段属于我解释的应用链路。

### 备查层：四个观察位置

沿 `src/routes/profiles.ts` 看 `segmentsPatchSchema → toSegmentPatch`，再沿 `src/stores/agent-profiles.ts` 看 `AgentProfileStore.update → restore`。只解释这次请求实际经过的对象，不先展开身份哈希、所有发布入口和数据库底层锁。

创建与更新各自使用独立 Schema；`toSegmentPatch` 只转发不是 undefined 的字段；存储层用旧值填充未提供的段。update 与 restore 是独立函数，都先保存当前内容快照，再更新四段与版本；不要说 restore 实际调用了 update。**这两条路径没有把快照和更新包进显式多语句事务**；setDefault 中另有事务，也不能证明内容更新或草稿发布原子化。[路由][profile-routes] / [存储][profile-store]

定位结果按六项复盘记录：原输入、原预期、实际对象在哪一步变化、具体改了哪一层、保存前后差异、尚未覆盖什么。没有真实观测记录时，不补写“我当时查了一晚数据库，最后才发现”。

### 失败验证：看保存前后，不看 HTTP 成功就结束

| 检查 | 应观察的结果 | 证据性质 |
|---|---|---|
| 只更新一段 | 另三段逐字段不变，版本递增 | 已有存储层局部更新测试定义 |
| 显式传空字符串 | 指定段清空，未指定段保留 | 本文建议的接口边界演练，本轮未执行 |
| 修改后看历史 | 旧快照仍有原内容，不被新值覆盖 | 已有存储层测试定义 |
| 恢复旧快照 | 内容回到旧四段，但当前版本继续增加 | 已有存储层测试定义 |
| 比较请求与解析对象 | 未传字段不会因创建默认值进入补丁 | 本文建议的接口边界演练，本轮未执行 |

已有测试不等于上述每个接口场景均已运行通过。面试展示优先拿一组更新前后的内容，不需要发明性能数据。[测试][profile-tests]

**讲不深时：**“我能完整解释缺失、空字符串、字段转换和保存结果；并发编辑与完整发布事务是另外的问题，不扩大这次实现的范围。”

## 难点二：统一了消息格式，怎么保证消息仍然进入正确会话？

**面试主问：**“IM 接入除了调用 SDK，还有哪些具体工作？”

**证据性质：**消息模型、挂载解析、入口准入及多账号回归定义。依据：[统一消息对象][im-contract]、[ImManager][im-manager]、[ImIngress][im-ingress]、[安全回归][im-tests]。

### 六项复盘

| 项目 | 内容 |
|---|---|
| 操作 | 同一工作站接收不同账号、群、私聊或话题的消息，并回复 |
| 预期 | 格式统一，但原账号和会话位置不能丢；不能串上下文或换账号回复 |
| 现象／异常输入 | 只按渠道取适配器，在同渠道多账号下无法准确区分；不合法挂载如果先分配会话，会留下不应产生的记录。这些有测试构造，不宣称真实消息曾泄露 |
| 定位 | 消息规范化保留了什么、挂载键如何构造、何时分配 Session、出站取哪个适配器 |
| 调整 | 保留 channel/accountId/conversation/senderId；按账号定位挂载和适配器；先检查资源再分配会话 |
| 结果 | 消息按有效挂载进入相应会话；指定账号不存在时不换另一个机器人代发；拒绝请求不应先创建会话副作用 |

### 主动介绍

> IM 归一化不能只保留一句文本，还要保留它从哪个账号、哪个会话进来。否则单机器人测试看起来能跑，多账号或话题场景就容易定位错。我把账号和会话信息保留在统一消息里，先检查准入和挂载资源，再定位会话；回复也使用指定的来源账号。找不到账号或挂载时明确拒绝，不做可能换错身份的兜底。这样统一的是入口接口，不是把不同消息的身份信息抹平。

**主动收口：**“这一点我讲消息怎样进对地方、由对的账号回复，不把它说成跨重启可靠投递。”

### 第一层追问：一个例子讲清两个边界

假设两个 Telegram 账号 A、B 都配置在平台，消息会话编号即使相同，也需要通过账号信息区分挂载。A 收到的消息，出站必须找到 A 对应的适配器；A 不存在时不能随便使用 B。这个例子检查的是账号定位，不是消息是否至少投递一次。

群挂载指向工作区；私聊或按相应方式配置的原生话题可以指向稳定会话。存在 threadId 时，当前会话键包含话题标识；**仍需要有效挂载和正确 kind 配置，不是收到任何话题就自动创建隔离会话**。[解析实现][im-manager]

| 追问类别 | 回答 |
|---|---|
| 架构：为什么不直接收到文本就调用模型？ | 先确定请求对应的账号、资源和会话，才能避免上下文与回复身份混用 |
| 实现：关键字段是什么？ | 第一层只说 accountId 和 conversation；再问时解释 channel、senderId、messageId 分别保留什么，不把它们混作一个身份 |
| 取舍：没挂载能不能自动找一个默认会话？ | 当前不这样兜底，因为无法证明目标资源与上下文正确；明确拒绝比悄悄投到错误位置更可诊断 |
| 失败：最终拒绝了就行，为什么还管先后顺序？ | 分配会话、写消息已经是副作用；拒绝路径除了不调用模型、不发送，还应检查没有新增错误会话 |
| 职责：你实现的是什么？ | 应用消息契约、挂载与账号定位、入口校验及出站选择；渠道 SDK 与模型循环保留依赖来源 |

### 备查层：从哪里看

`ImManager.adapterKey` 使用 channel 与 accountId；`conversationKey` 在存在 threadId 时把它加入会话键；`mountForMessage` 可先读取挂载而不分配会话；`resolveMount` 才做会话校验或分配。生产装配通过 `ImIngress.handleInbound` 先做账号、准入与工作区检查，再进入后续解析与运行。不能拿 Manager 的底层解析函数本身说成已经做完全部授权。

已有回归用例故意先注册 B、再注册 A，分别发送并检查实际适配器；缺失账号必须报错而不是回退。另有拒绝管理命令时检查模型调用、发送记录、会话和消息记录均为空的用例。本轮未运行这些测试。[回归定义][im-tests]

当前飞书、Telegram 有 SDK 适配，其余五个为骨架。连接、真实入站与模型往返、可靠重投是不同验收；消息里有 messageId 也不等于已经完成去重。

**讲不深时：**“我能沿账号和会话键追到目标 Session，并解释拒绝发生在分配之前；消息队列、持久 outbox 和跨重启补发不是这次已实现结论。”

## 难点三：扫描到一条任务，为什么还不能直接执行？

**面试主问：**“定时任务为什么还需要认领？”

**证据性质：**当前调度器与认领测试定义；不冒充多进程生产实验。依据：[调度器][scheduler]、[调度测试][scheduler-tests]。

### 六项复盘

| 项目 | 内容 |
|---|---|
| 操作 | 定期扫描计划，并执行应该发生的一次任务 |
| 预期 | 同一计划时点不重复建执行记录，读到记录也不能绕过认领条件 |
| 现象／异常输入 | 同一发生点反复扫描，或两个执行者依次尝试认领同一条记录；已有测试构造，不虚构线上重复通知 |
| 定位 | 发生点物化与 worker 认领是两个步骤，不能都交给内存布尔值 |
| 调整 | occurrence 唯一键限制重复建行；条件 UPDATE 决定认领是否成功，再根据更新结果执行 |
| 结果 | 发生点记录去重，状态持有权和更新有条件约束；不由此宣称任何外部动作都恰好一次 |

### 主动介绍

> 定时任务我区分了两件事：这一次计划是否已经生成记录，以及当前执行者有没有拿到处理权。同一时点可能被反复扫描，所以先用发生点唯一键避免重复建行；看到记录后还要做条件更新，更新成功才继续执行。这样不会把“查到任务”误当成“已经认领任务”。我当前能说明的是记录去重和状态更新条件，外部动作是否重复需要另外处理。

### 第一层追问与备查

| 追问类别 | 回答 |
|---|---|
| 架构：唯一键和认领不是同一件事吗？ | 唯一键限制一个发生点建几行，认领限制哪一个执行者能更新已有运行记录，约束对象不同 |
| 实现：谁判断认领成功？ | claimOne 的条件 UPDATE 及受影响行数；不是查到候选就返回成功 |
| 取舍：只用内存锁呢？ | 只能约束当前实例，不能表达数据库里是否已有该发生点；但使用数据库也不自动获得完整分布式保证 |
| 失败：过期任务都重跑？ | 不这样概括。已开始任务的外部动作可能已经发生，当前对已开始且过期的运行标失败、不自动复活 |
| 职责：自己做了什么？ | 围绕计划发生点、条件认领和运行记录复现实现应用链，不能把整个调度可靠性都算成已验收成果 |

输入例子：用同一个计划时点重复物化，检查只有一行；两个认领者尝试同一行，检查谁的条件更新生效。这是待演练对象。现有首个双认领测试在同一数据库连接上顺序调用两个实例，不能包装成多进程竞争和崩溃全部通过。

备查时再说明 owner/token 参与后续状态更新，限制旧持有者写回；Clawtide 认领路径没有将查询与更新包进显式多语句事务，上游版本的事务式路径不能代答。SQLite 底层的事务性也不能被说成“不存在任何事务”。

常规 candidates 只扫描 queued/retry_wait；服务启动的 recoverOnStart 才释放符合条件的未启动 running 行。两种入口不同，启动释放也没有证明其他持有实例已失活。续租失败当前只停心跳、写日志，没有取消执行器。以上留在明确追问时解释，不在开场主动承诺多实例安全接管。

**收口：**“我先把发生点和状态持有权讲准确，没有把记录去重扩大成外部副作用恰好一次。”

## 难点四：已经登录了，为什么仍然不能操作这个工作区？

**面试主问：**“项目里的权限不是判断一下管理员就行了吗？”

**证据性质：**当前资源授权函数与入口行为；下方小表是由规则推导的演练预期，不是本轮测试结果。依据：[rbac.ts][rbac]、[IM 入口][im-ingress]、[拒绝副作用回归][im-tests]。

### 六项复盘

| 项目 | 内容 |
|---|---|
| 操作 | 登录用户读取、修改或删除某个工作区 |
| 预期 | 身份合法还必须对这一个资源、这一个动作有权限 |
| 现象／边界例子 | 简单用管理员角色放行会绕过资源归属；只隐藏按钮也无法替代服务端检查。这是规则设计问题，不宣称发生过越权泄露 |
| 定位 | 登录认证之后、资源动作之前的应用授权层 |
| 调整 | 明确请求者、工作区所有者及动作，使用独立读/改/删检查；Home 保留禁删规则 |
| 结果 | 非所有者不因管理员身份直接通过这些函数，Home 删除被拒绝，归属无法解析时默认拒绝 |

### 主动介绍

> 我把登录身份和资源权限分开。登录只能说明平台知道你是谁，不能说明你能操作所有工作区。应用在读、改、删之前分别检查请求者和工作区归属，不因为管理员角色就自动跳过所有权；Home 还保留独立的禁删规则。这样权限落实在服务端的具体动作上，而不是只靠前端隐藏按钮。

### 第一层追问：用一个小表解释，不先讲完整安全体系

以下仅讨论有明确 created_by 的普通 Web 工作区及 Home，不扩大到所有历史数据分支。[规则实现][rbac]

| 请求者与资源 | 读取/修改 | 删除 |
|---|---|---|
| 普通工作区的所有者 | allow | allow |
| 另一个用户，即使角色为 admin | deny | deny |
| Home 的所有者 | allow | deny |

| 追问类别 | 回答 |
|---|---|
| 架构：认证和授权分别做什么？ | 认证建立请求身份，授权判断这个身份对目标资源的动作；两者不能互相替代 |
| 实现：三个函数返回三种状态吗？ | 不是，读、改、删是三个动作函数，各自返回 allow 或 deny |
| 取舍：为什么不给管理员兜底？ | 当前资源政策以所有权为依据；系统管理权限与用户工作区访问不是同一项授权 |
| 失败：老数据没有所有者怎么办？ | 特定 IM 历史行可从同目录 Home 推导归属，推不出来就拒绝，不凭空选一个 Owner |
| 职责：自己能展示哪段？ | 展示资源对象、三个检查入口和上述几个允许/拒绝例子，不把这层等同于容器或工具级隔离 |

备查时看 `canAccessGroup / canModifyGroup / canDeleteGroup → decide`。这组函数不使用 admin 角色形成所有权旁路。IM 中 senderId 用于受众判定，账号拥有者参与工作区授权；everyone 普通消息可继续，不代表发消息的人变成了工作区 Owner。[入口][im-ingress]

**收口：**“这一层回答谁能对哪个工作区做什么，不直接承诺模型所有工具的行为都受同样限制。”

## 难点五：浏览器还有 Cookie，为什么服务端仍然拒绝？

**面试主问：**“会话存在和用户仍然登录是一回事吗？”

**证据性质：**当前认证实现、撤销与过期测试，以及登录失败计数实现。依据：[AuthService][auth]、[认证测试][auth-tests]、[两层计数][rate-limit]、[计数测试][rate-tests]。

### 六项复盘

| 项目 | 内容 |
|---|---|
| 操作 | 浏览器携带已有 Cookie 再次访问管理入口 |
| 预期 | 服务端已撤销或过期的会话，不因浏览器仍保存 Cookie 而继续生效 |
| 现象／异常输入 | 一个签名仍正确的旧 Cookie，在对应数据库会话被删除或过期后继续提交；已有测试定义，不虚构实际身份盗用 |
| 定位 | Cookie 签名检查和服务端有效会话查询的衔接 |
| 调整 | 签名通过后仍按 token 查会话和用户，检查有效期；撤销删除服务端记录，登录失败另计数 |
| 结果 | 正确签名不再被等同于当前会话有效；旧 Cookie 无有效记录时不能解析出用户 |

### 主动介绍

> 我没有把“浏览器还带着 Cookie”当成仍然登录的依据。请求先检查签名，再去服务端查询这份会话是否存在、是否过期；用户退出后会话记录删除，即使浏览器还保留旧值，也不能继续解析出用户。登录失败次数则单独按账号相关维度记录。这让客户端持有凭据和服务端当前是否认可它分开，而不是只要验签成功就一直放行。

### 第一层追问与备查

| 追问类别 | 回答 |
|---|---|
| 架构：为什么验签还要查库？ | 签名用于检查携带内容是否匹配签名规则，数据库决定这份会话现在是否仍存在和有效 |
| 实现：怎么演示？ | 创建会话后 resolveUser 能返回用户；删除对应会话，再提交同一个 Cookie，不能解析出用户 |
| 取舍：为什么不是完全无状态？ | 当前需要用服务端记录表达撤销和有效期；接受查询成本，不声称比较后证明所有无状态方案都不合适 |
| 失败：签名没错但过期呢？ | 仍然拒绝；当前还会删除已过期记录。正确签名不证明凭据没有被窃取，也不单独防止重放 |
| 职责：自己与依赖各做什么？ | 我复现实现会话创建、查验、撤销和计数接线；密码学原语使用标准库，不认领自研加密算法 |

备查入口是 `src/auth.ts::AuthService.resolveUser`，先 `verifySignedCookie`，再连接 user_sessions 与 users 查询并判断过期。已有测试包含 create → resolve → destroy、强制过期和篡改拒绝。[测试][auth-tests]

两层登录计数分别以“账号＋IP”和“跨 IP 的账号累计”为键，均在进程内；成功登录只清除对应第一层记录，第二层按自己的窗口自然过期。没有纯 IP 跨账号总计数，也不自动跨实例共享。[实现][rate-limit]

**只在明确问部署时补充：**当前 `isSecureRequest` 实际只看 socket 是否加密，不因注释提及代理就假定使用 X-Forwarded-Proto；IP 提取中的 TRUST_PROXY/X-Forwarded-For 是另一逻辑。反向代理与浏览器 Cookie 行为需要实际部署验收，不能沿用注释补造功能。

**收口：**“我讲的是服务端会话有效性与尝试计数，不把它扩大成完整工具安全或分布式限流。”

## “遇到困难后怎么解决”和“还没达到预期”不要混成同一个故事

### 已有机制可以讲清楚

Profile 的字段语义、IM 的账号定位、发生点与认领分离、资源动作检查、服务端会话有效性，都有可指认的应用层对象。这些可以正常讲本人复现实现，不需要每段先说一遍“我还没有完成”。

### 尚未闭环的地方，作为复盘题回答

| 被问到的现象 | 当前事实 | 后续方案，尚未实施 |
|---|---|---|
| 同一个 AgentRuntime，定时结果却不能直接视为采用同一人设 | 当前定时 executeRun 未传 Profile systemPrompt | 先明确入口身份、配置选择和会话策略，再补执行上下文及对照验证 |
| 日志显示失租，执行器是否真的停了 | 当前只停心跳并写日志，没有失租到执行器的取消接线 | 传播取消，验证旧执行者仍存活时的行为；外部动作另定义幂等 |
| 草稿已确认，但发布回调失败 | confirmed 在回调前写入，存在非原子窗口 | 先校验草稿，再定义事务或可恢复发布状态，不把“确认”当“发布成功” |
| IM 普通回复发送失败 | 当前记录错误，没有完整持久化 outbox | 明确投递状态、重试和去重策略后再实现，不凭一次发送成功称可靠投递 |

依据：[服务入口][server]、[调度器][scheduler]、[草稿存储][profile-store]、[IM 入口][im-ingress]。这些是已知限制，不是本次新文档修复了业务代码。

### 可以直接使用的一段“预期不符”回答

> 一个值得复盘的地方是：把入口接到同一个运行函数，并不自动让它们使用同样的配置。当前 Web 和 IM 可以选择 Profile，但定时执行没有把这份提示词传进去。所以我没有把共用函数当成配置一致的证据，而是把入口参数的差异明确列出来。后续应先确定每个入口怎样选择身份、会话和配置，再做对照验证。这是接线仍需补齐的地方；已有调度记录和 Profile 管理能力可以分别说明，不能混成一个已完整闭环的承诺。

只有你确实重现过输出差异，才能把开头换成“我运行后观察到……”。单看缺少参数的源码，只能说存在接线差异，不提前断言模型一定表现出某一种结果。

## 遇到连续深挖时，怎样保持回答具体

**“这是不是一个很基础的问题？”**

> 单个字段判断本身不复杂，我重点说明的是用户编辑意图怎样经过请求解析、转换和保存仍保持一致，以及如何用前后内容验证。这个点不需要包装成复杂基础设施，但它直接影响应用结果。

**“你怎么证明不是背代码？”**

> 我会用一个变体输入推导结果。比如把“只改 tools”换成“显式清空 tools”，或把“已有账号”换成“缺失账号”，先说保存、会话或发送记录应该怎样变化，再打开相应处理位置核对。

**“都是你独立原创的吗？”**

> 不是。我基于 HappyClaw 参考架构，围绕五个选点复现并实现应用能力；SDK 和上游已有部分保留来源。我重点解释自己负责的应用输入、状态、调整和验证，不把整个生态算成原创。

**“为什么不用更复杂的方案？”**

> 先看要保证的对象。局部编辑先保证未传字段不变，任务认领先保证条件更新，入口先保证资源和身份定位。复杂方案可以讨论，但必须对应额外需求，而不是为了让项目听起来更大。

### 演练顺序与检查记录

先把 Profile 两种请求说清，接住“为什么不全量更新”和“恢复为什么是新版本”；再讲 IM 的来源账号与挂载。剩下三点分别用一行数据库记录、一个资源对象、一个旧 Cookie 解释，不在一次回答里全部展开。

| 每次演练记录 | 填写方式 |
|---|---|
| 操作与输入 | 写出真实请求或本次构造的样例，标明是哪一种 |
| 预期 | 指定哪几个字段、状态或副作用应该变化／不变 |
| 实际现象 | 只填实际观察，不把预期复制成通过结果 |
| 定位与调整 | 哪一层输入输出不符合约定，具体改了什么；没有改代码就写检查或设计 |
| 复验 | 版本、命令或操作、实际输出及结论 |
| 取舍 | 当前方案明确未覆盖的一个范围，不另外展开整套系统 |
