### R14 · 任务物化、租约与副作用

**依据：** E01、E02、E13、E19；对齐简历“任务物化与条件认领”。

#### Q14.1 为什么要先把定时任务物化成执行记录，而不是到点直接调用模型？

**题源：** R 点基线 + 当前源码核验

直接在计时器回调里执行，很难区分“同一计划时点被重复扫描”和“确实应该新增一次执行”。当前实现把发生点写成带 occurrence_key 的 task_runs 行，插入遇到唯一键冲突就不重复创建，然后用条件 UPDATE 认领，受影响行数决定是否拿到该行。这样任务定义、计划发生点和执行状态分别可查；代价是要管理更多状态与过期分支。这个机制证明的是数据库层的去重与认领，不是模型调用或外部消息天然恰好一次。

**边界提醒：** 接口层重复请求、发生点重复扫描、同一次执行中的工具重试不是同一种去重；必须分别定位键和状态。

#### Q14.2 Clawtide 的认领到底有没有事务？lease_token 能保证什么？

**题源：** 当前实现深挖／场景追问

我会按实际版本答，不把上游与自己的工程混在一起。Clawtide 的 claimOne 先读取候选，再执行带状态条件的单条 UPDATE，以 changes 判断赢家；这里没有包住查询与更新的显式多语句事务，而上游评审引用的是事务式路径。后续开始、续租与结束更新包含 owner/token 条件，用来限制旧持有者写回任务状态。它不能阻止已经发出的外部请求，SQLite 单写者也不意味着其他多步操作无需事务。

**边界提醒：** 首个双认领测试定义在同一连接上先后调用两个实例，只覆盖这种调用条件下的裁决，不能当成已通过的多进程崩溃实验。

#### Q14.3 租约到期或通知失败时，任务怎样恢复？

**题源：** 当前实现深挖／场景追问

恢复分常规运行与服务启动两条路径。常规 candidates 只扫描 queued/retry_wait，因此不会把 running 的过期未启动行送入 claimOne；服务启动已调用 recoverOnStart，将符合条件的 running 未启动行释放为 retry_wait。已启动的过期行由扫描标为 failed，不自动重做。启动恢复已接线，但释放条件没有证明原持有实例已失活，不能推广成多实例安全接管。续租失败只停止心跳和记录日志，没有取消执行器；notification 写任务日志，也不是 IM 补发。技术产物是这些可定位的状态规则，完整故障行为、外部幂等与通知投递仍需分别验收。[E02、E19；固定源码 task-scheduler.ts:630–674、server.ts:290]

**边界提醒：** “日志写着 aborting”不是调用了 abort；人工重新运行也要核查固定 :now 唯一键的限制。

### R15 · Profile 分段与变更确认

**依据：** E03、E04、E05、E14、E19；对齐简历“Agent Profile 与配置变更”。

#### Q15.1 为什么把数字员工配置拆成四段？

**题源：** R 点基线 + 当前源码核验

身份、行为原则、工作规则与工具偏好混在一段文本中，局部修改容易连带覆盖不相关内容。当前 ProfileSegments 分别保存四个字段，buildSystemPrompt 将非空字段放在平台前导块之后；更新只替换显式提交的字段，修改前保留四段内容快照，恢复时生成新版本而不是覆盖历史。这样配置对象可以局部维护和回看，但仍是声明式文本，不能把 AGENTS 段说成可执行工作流，也不能把平台文字当作不可突破的权限边界。

**边界提醒：** append/replace 在当前组装函数中主要体现为模式标记；不要拿上游更完整的继承合并语义代答。

#### Q15.2 PATCH 中没传某字段，和把字段设为空，有什么不同？

**题源：** 当前实现深挖／场景追问

没传字段意味着保留旧值，传空字符串意味着用户主动清空。当前 routes/profiles.ts 为 PATCH 单独定义不带默认值的 segmentsPatchSchema，toSegmentPatch 仅转发不是 undefined 的键，存储层再保留未提供字段。这避免把创建接口的空默认值带进 PATCH 后清空其他配置。对应测试定义检查局部更新、版本快照与恢复；这是我负责复现实现的配置链，不把代码注释中的问题编成亲历生产事故。

**边界提醒：** 讲解可对照未传字段与显式空值两种请求，追踪Schema、存储和快照；实际回归结果另按运行记录说明。

#### Q15.3 确认短语是不是保证所有配置修改都经过人工审批？

**题源：** 当前实现深挖／场景追问

不是。当前草稿入口从已认证Web用户取得PublishContext，用所有者、草稿状态、过期时间与精确短语决定是否调用发布；直接创建和PATCH另有入口，不统一经过草稿确认。草稿JSON由客户端提交，不能仅凭这个入口就声称实现AI自动生成。confirmDraft还存在先写confirmed再调用publish回调的顺序，回调抛错时可能出现草稿已消耗而配置未发布，所以它不是完整的原子发布事务。

**边界提醒：** 定时入口目前没有注入Profile提示词；模板配置存在，不等于三个入口都已使用同一策略。

### R07 · 渠道适配与会话定位

**依据：** E06、E07、E08、E09、E18；对齐简历“IM 适配与会话接入”。

#### Q07.1 为什么需要 ImChannelAdapter，而不是每个机器人单独调用模型？

**题源：** R 点基线 + 当前源码核验

每个渠道单独写一套调用链，会重复处理账号、消息格式、会话定位和出站回复。当前接口统一start/stop/send及capabilities，InboundMessage显式保存channel、accountId、conversation、senderId和messageId；入口再按挂载找到工作区或会话，交给统一runtime。这样渠道差异主要留在适配层。取舍是不能用公共接口掩盖渠道差异，能力声明也不是对应功能已经完整实现的凭证。

**边界提醒：** 当前两个SDK适配是飞书与Telegram，其余五个是骨架；不会把上游的七渠道能力当个人实连数量。

#### Q07.2 消息里的群、私聊和话题，怎样对应工作区和会话？

**题源：** 当前实现深挖／场景追问

handleInbound先查渠道账号并检查渠道一致性，然后做Owner Gate，再读取已持久化的mount；确认目标工作区存在且账号所有者具有访问权限后，才让manager解析或分配会话。direct/thread绑定可定位特定会话，group路径复用或创建工作区会话，再进入串行runtime。这样无效或跨归属绑定不会先产生会话副作用。这里讲的是应用层资源定位，不是所有渠道行为完全相同，也不等于操作系统隔离。

**边界提醒：** 先校验挂载和归属再分配会话，是可以直接展示代码顺序的关键细节。

#### Q07.3 接通渠道、完成一轮回复、可靠投递，是不是同一验收？

**题源：** 当前实现深挖／场景追问

不是。SDK实例能建立连接，说明连接配置至少可用；收到真实入站、完成模型调用并发回回复，是更长的验收链；崩溃后补投、重复消息去重又是另一层。README记录了两个渠道的连接信息，但本轮没有使用真实凭据复验。当前IM路径调用manager.send，失败捕获后记录日志，没有完整持久化outbox，因此不能写成消息至少一次交付或跨重启自动补发。

**边界提醒：** 消息对象具有messageId，不代表已经用它实现幂等去重。

### R20 · 动作授权与 IM Owner Gate

**依据：** E07、E08、E10、E11、E15；对齐简历“工作区授权与 IM 准入”。

#### Q20.1 管理员为什么不能任意访问和删除别人的工作区？

**题源：** R 点基线 + 当前源码核验

系统管理身份与工作区资源归属不是同一权限。当前三个检查函数把access、modify、delete作为不同动作交给decide；普通工作区以created_by或遗留归属解析结果判断，Home只有所有者可读改且任何人都不能删除。角色参数并不提供所有权旁路。这让授权判断可单独测试，但它只是应用资源授权，不是完整多租户运行时、文件系统或容器隔离。

**边界提醒：** 所谓“三态”在这里应解释为三类操作检查，函数返回实际只有allow/deny。

#### Q20.2 非 Owner 发消息一定会被静默丢弃吗？

**题源：** 当前实现深挖／场景追问

不一定。checkOwnerGate先处理disabled，再处理保留管理命令，然后根据owner身份和audience_mode判断普通消息。owner_only下非Owner被静默拒绝，everyone下普通消息可以继续；/bind与/unbind目前连Owner也不执行，因为命令只是保留。实际server装配没有传audienceMode，入口默认everyone。因此不能把这个项目讲成所有消息默认只允许Owner，也不能把未执行的管理命令讲成已完成绑定功能。

**边界提醒：** everyone只是准入层的产品选择，后续仍检查渠道账号绑定工作区的访问权；不是自动证明工具级授权安全。

#### Q20.3 为什么在分配会话前检查挂载和工作区归属？

**题源：** 当前实现深挖／场景追问

如果先创建Session再发现挂载无效或属于其他用户，即使最终没有执行模型，也会留下不应该产生的状态。当前IM入口在manager.handleInbound之前读取mount，确认workspace存在，再以channel account所属用户检查canAccessGroup；未通过就返回，后面才解析会话并检查绑定的Profile。这个顺序减少拒绝路径的状态副作用，但运行期权限变化、工具访问范围仍应另行核对，不能从准入顺序推导整个系统所有路径都已安全。

**边界提醒：** 跨渠道身份不按显示名自动合并；Owner身份来自各渠道原生ID的绑定。

### R19 · Cookie 身份认证与限流

**依据：** E12、E16、E17；对齐简历“会话认证与登录限流”。

#### Q19.1 为什么既有随机 token，又给 Cookie 做 HMAC？

**题源：** R 点基线 + 当前源码核验

随机token标识服务端会话，数据库保存它的用户与有效期；HMAC给客户端携带的token加完整性验证。resolveUser先验证token.sig的签名，再查数据库会话和用户，过期或已注销就拒绝。签名比较使用timingSafeEqual，但查库不是常量时间比较。这个设计没有把Cookie变成加密内容，HMAC也不解决所有会话窃取风险；传输条件、XSS与会话吊销要分别考虑。

**边界提醒：** 不要把这条Web用户认证说成Agent运行时身份或IM命令授权。

#### Q19.2 两层登录限流具体按什么维度？

**题源：** 当前实现深挖／场景追问

当前第一层键为username:ip，第二层为user:username，在同一个进程内跨IP累计失败。成功登录只清第一层，避免用一次成功登录重置账号跨IP累计。两个计数都保存在内存Map，窗口到期清理，所以“global”仅表示跨IP账号维度，不代表多实例共享；也没有独立的纯IP维度，单IP尝试大量用户名的密码喷洒仍是盲区。

**边界提醒：** 这条内容适合展示数据结构、窗口和失败分支，不用“彻底防爆破”这种结论。

#### Q19.3 __Host- Cookie 在本地 HTTP 和反向代理下如何处理？

**题源：** 当前实现深挖／场景追问

当前AuthService根据secureRequest选择带__Host-前缀的HTTPS名称或普通HTTP名称，并分别设置Secure、HttpOnly、SameSite和Path等属性。Cookie的Secure判定中，isSecureRequest只判断socket是否加密；限流IP提取则已在TRUST_PROXY=true时读取XFF，不能把两种用途混为一谈。因此我只按已检查的函数说明行为，不宣称任何TLS终止代理都已经配置正确；实际部署要核对浏览器收Cookie、代理可信边界和HTTP/WebSocket读取会话是否一致。

**边界提醒：** 本轮没有运行TLS、真实浏览器登录或分布式限流验收。

| 架构 | HMAC、RBAC和Owner Gate谁先谁后？ | HMAC属于Web认证；RBAC是资源动作授权；Owner Gate是IM准入，不能合成一个抽象“安全模块”。 |
| 实现 | 签名合法但DB会话删除了呢？ | resolveUser查不到会话仍拒绝，不能只凭签名通过认证。 |
| 取舍 | 为何保留服务端会话？ | 可以用DB有效期与删除控制存活；代价是查库和共享部署策略，不能说无状态认证。 |
| 失败 | 进程重启后限流记录怎样？ | 内存计数丢失；多实例也不共享。需要时用共享存储或网关策略，但这是扩展方向。 |
| 个人贡献 | 安全结果如何证明？ | 我负责复现实现签名、DB会话与两层计数；伪造签名、失效会话、窗口到期等运行结果另列，不声称通过全面安全审计。 |

**风险与降级：** 中：HMAC与加密混淆、账号+IP与纯IP混淆、跨IP与分布式混淆。

## Part 2 · 场景专属追问

**题源：**下列五题均为 [scenario-specific]，基于运营演示场景；未提供具体JD，不冒充某家公司实际面试题。

### 跨境电商到底落在哪里？

落在演示输入与工作方式，不是自动接入业务系统。可以手工提供“订单延迟、库存待核实、需回复事项”的脱敏文本，让IM入口做整理，再在定时任务中运行同类文本任务并查看记录。缺少ERP、库存和汇率Adapter时，不能说Agent已经自动监控这些指标。样例文件见 `fixtures/运营简报-演示输入.md`，该文件为既有人工演示样例，不是用户真实订单。

### 定时生成日报后能自动发到飞书吗？

当前不能凭调度器notification字段这样承诺。该路径写的是task_run_logs，IM普通回复是另一条send链。要把定时结果可靠发到飞书，需要目标账号/会话配置、投递状态、失败重试、权限与重复处理的接线和验收。[E02、E07]

### 相同Profile能保证Web、IM、定时三端行为一样吗？

不能。当前定时executeRun没传入Profile系统提示词；Web与IM的Profile选择也不能只看数据表就假定完全一致。即使输入一致，模型输出仍需单独评估，不能用配置版本或类型检查代替行为质量。[E03、E07、E19]

### 为什么不把它包装成全自动智能客服？

因为当前证据没有证明真实客户知识、订单状态、退款审批和人工转接这些业务环节。更准确的定位是可自托管的数字员工工作站，聚焦消息接入、定时任务和应用治理。演示可覆盖整理建议，外部高影响写动作不能凭Prompt假定安全。

### 没有RAG，是不是完全没有上下文？

不是。会话和SDK执行仍有上下文概念；缺少的是可证明的知识库检索/向量索引方案。这里不把普通历史、Profile文本或任务表改称RAG，也不把未验证的SDK恢复行为说成完整长期记忆。[E18]

## Part 4 · 每条简历的故事摘要

[story summary - see Step 1c for full version] 以下为每点约30秒第一人称STAR摘要；[完整八模块故事](HappyClaw-故事.md)的M5提供90秒与3分钟讲法，M6提供逐轮展开追问。

### R14 · 任务物化与条件认领

运营事项需要按计划处理时，我希望同一个发生点有唯一记录，执行状态也能追踪。我在复现中用 occurrence 唯一键物化 run，以条件 UPDATE 认领，再带 owner/token 写回。技术产物是发生点去重和受条件保护的状态链；外部动作恰好一次不在这个保证内。

**最关键防线：**发生点与状态写回有条件约束；启动恢复已接线，常规pump与失租取消另有边界，不承诺端到端exactly-once。

完整展开见[故事M5与M6](HappyClaw-故事.md)，对应 Q14.1–.3。

### R15 · Profile 局部修改与历史维护

数字员工规则混成整段文本时，局部更新容易覆盖其他内容。我负责复现实现四段 Profile、PATCH 字段保留和内容快照，恢复也生成新版本，形成可局部维护和回看的配置链。草稿短语只确认该入口的发布意图，配置文本本身不承担硬权限。

**最关键防线：**草稿短语只覆盖该入口，CRUD另路；配置文本不是硬权限，发布也不是原子事务。

完整展开见[故事M5与M6](HappyClaw-故事.md)，对应 Q15.1–.3。

### R07 · IM 适配与会话接入

用户从不同 IM 提交运营文本时，账号和会话定位不能跟着渠道格式各写一套。我负责复现实现适配接口与统一入站对象，让消息经过挂载和授权后进入 runtime。产物是飞书、Telegram 的 SDK 适配及共用接入链；另外五个渠道保持骨架。

**最关键防线：**两个SDK适配、五个骨架；连接、模型往返、可靠投递分别验收。

完整展开见[故事M5与M6](HappyClaw-故事.md)，对应 Q07.1–.3。

### R20 · 资源动作授权与受众策略

管理角色和工作区所有者混用，会让入口不知道谁能操作资源。我负责复现实现读、改、删三类授权与 IM 准入，形成所有权检查、Home 禁删及拒绝后不执行的分支。当前 IM 默认 everyone，普通消息准入后仍按渠道账号所属用户检查资源访问。

**最关键防线：**三个动作各返回allow/deny；默认everyone普通消息可继续，后续按账号所属用户做资源授权。

完整展开见[故事M5与M6](HappyClaw-故事.md)，对应 Q20.1–.3。

### R19 · 会话认证与登录尝试约束

Web 管理入口需要先知道用户身份，再处理资源。我负责复现实现随机会话 token、HMAC 核验和有效会话查库，并按账号加 IP、跨 IP 账号两层记录登录失败。产物是失效会话拒绝和账号尝试约束；签名不加密 Cookie，进程内计数也不等于分布式限流。

**最关键防线：**HMAC核验完整性后仍查DB；两层账号计数在进程内，Cookie与限流IP的代理判定分别说明。

完整展开见[故事M5与M6](HappyClaw-故事.md)，对应 Q19.1–.3。
