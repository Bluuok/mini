## 难点一：接口已经返回，研究任务到底算不算完成？

**面试主问：**“这个项目里，你处理过什么比较具体的难点？”

**证据性质：**有当前实现、生命周期测试定义和历史整改记录。历史记录说明项目处理过这些问题，但不能替代本人具体排障经过。依据：[提交与终态实现][lifecycle]、[生命周期测试][lifecycle-tests]、[历史整改记录][review-record]。

### 六项复盘：把问题限定在一次提交上

| 项目 | 可以讲清楚的内容 |
|---|---|
| 当时要完成的操作 | 用户发起一个需要持续执行、逐步返回内容的研究任务 |
| 原本预期 | 提交后能明确知道是否受理；运行中能看状态；结束后能回看结果 |
| 实际现象／故障切片 | 项目整改记录涉及受理、重复提交、忙碌拒绝和中断恢复；测试具体构造“模型尚未结束”“相同请求重复提交”“取消时已有部分文本”。不是一份线上事故日志 |
| 定位到哪一层 | 提交受理、后端执行、文本保存及终态通知之间的交界，而不先归因于模型回答能力 |
| 具体调整 | 同步预留会话状态，先保存受理信息，返回运行标识；后续执行单独推进，保存结果和终态后再通知完成 |
| 调整后的可观察结果 | 提交返回时模型仍可运行；重复请求关联原执行；被忙碌拒绝的请求不留下幽灵用户消息；取消保留已保存文本 |

### 主动介绍：先讲这一段

> 我在研究任务里重点处理了“提交成功”和“执行完成”容易混淆的问题。用户提交以后，模型可能还要继续搜索和分析，接口返回并不代表任务做完了。我把提交和执行拆开：先保存受理信息，给这次任务一个运行标识，再持续更新内容和状态；只有执行结束、结果和终态保存成功后，才通知完成。这样用户能区分任务仍在运行、已经取消或者确实完成，中断后也能回看已经保存的内容。

**主动收口：**“我解决的是任务状态和已保存结果能对应起来，不是承诺所有中断都自动续跑。”

### 第一层追问：五类问题，逐个回答

**架构问：为什么不让接口一直等模型结束？**

> 因为接口交互和研究执行不是同一个生命周期。长任务可以先确认受理，再通过后续状态告诉用户进度。把等待时间调长，并不能解释断线以后后台是否还在执行，也不能解决用户重试时是否启动第二次任务的问题。

**实现问：一个输入例子是什么？**

> 比如提交“比较两个框架”，返回的是 `accepted: true` 和一个 `runId`。此时后端仍可能在取材，不能把这个响应显示成“研究完成”。之后以这个运行标识关联文本和终态。注意 accepted 是受理响应，不是数据库里新增了一个同名执行状态。

**取舍问：requestId 和 runId 为什么不合成一个？**

> requestId 识别的是客户端这次提交意图，重试时应复用它；runId 识别服务端这次执行。相同请求标识和相同内容返回原受理结果，同一个标识换了内容则拒绝。相同文字也可能是用户主动重做，所以不能仅靠内容相同去重。

**失败问：模型说完成，但保存失败了呢？**

> 不能报告成任务成功。当前实现先刷新文本，再尝试保存终态；保存失败会把对外状态改为失败，不发布成功完成信号。失败时已有内容可能只保存了一部分，数据库也可能保留旧状态，所以要明确错误，不能把模型完成当成持久化完成。

**职责问：具体哪部分是你做的？**

> 我围绕这个选点复现并实现了应用层的提交受理、重复请求检查、执行状态和保存衔接。SDK 内部模型循环不是我写的；我负责的是它开始前和结束后，工作台怎样管理这次任务。

### 备查层：按这个顺序解释，不背整份源码

入口是 `apps/electron/src/server/session-manager.ts::SessionManager.submitMessage`。先检查请求缓存及历史记录，再判断会话忙碌；在第一次异步保存前设置处理中标记，避免两个并发提交都被当成空闲。受理保存失败时释放标记，不假装已受理。

后台消费事件时，模型 `complete` 暂不直接向外宣布成功。先经过 `RunTranscript.flush()`，再写 `lastRun`，最后依据实际状态发送完成事件或失败状态。重启入口 `recoverWorkspace` 把残留 `running` 标为 `interrupted`，不自动重放旧请求。[实现][lifecycle]

**定位路线不是虚构经历：**复盘时按“提交响应 → 是否创建运行记录 → 后端有没有结束 → 文本是否落盘 → 终态是否写入”逐层检查。同一处异常不要先跳到重试、分布式锁或模型超参数。

### 失败验证：看什么，不只是看“没报错”

以下是已有测试定义中的检查对象，本轮未重新执行。[测试][lifecycle-tests]

| 演练输入 | 应检查的结果 |
|---|---|
| 让测试后端暂停，不立即结束 | 提交已返回运行标识，但执行仍处于处理中 |
| 相同 requestId 和内容提交两次 | 测试后端只执行一次，受理结果一致，用户消息不重复 |
| 第一条未结束时提交另一条 | 返回忙碌拒绝，被拒绝文本不进入历史 |
| 已产生部分文本后取消 | 保留部分文本，终态为 cancelled，并调用取消入口 |
| 模拟重启前残留 running | 恢复后变为 interrupted，不把旧运行冒充成功 |

### 同一选点的备用故障：流式内容重复或缺段

**只在对方问“能讲一个具体显示或恢复问题吗”时展开。**历史整改记录提到重连文本重复／遗漏；当前实现可从 [RunTranscript][transcript] 核对。

> 我还处理了流式内容和最终文本的关系。比如先收到“A”、再收到“B”，最后又收到完整文本“AB”，如果把所有事件都追加，就会出现“ABAB”。我把同一回复段当成一个持续更新的消息：增量累积，完整文本覆盖这一段；保存时按稳定消息 ID 更新，而不是再插一条。增量另外带累计快照，为消费端补齐缺失文本提供依据。这样消息身份和内容版本能对应起来，代价是快照会增加传输量。

备查时说明：这一规则对应“同一段增量到完成”的当前处理；**不保证任意乱序或重复重放完成事件都天然幂等**。源码的检查点由事件到达触发，文本增量在距上次保存达到约 750ms 时刷新，不是无事件时也独立运行的周期定时器。强制退出仍可能丢失最后一个检查点之后的尾部。

**讲不深时：**“我能解释消息 ID、累计文本和保存检查点的分工；任意乱序重放及极端崩溃条件，要以额外回归为准。”

## 难点二：历史已经保存，为什么下一次不能全部送给模型？

**面试主问：**“你为什么专门做上下文处理？”

**证据性质：**Claude 适配路径的实现与确定性测试定义，不是对所有后端的统一承诺。依据：[历史选择实现][history]、[Claude 接入][claude]、[角色与预算测试][history-tests]。

### 六项复盘

| 项目 | 内容 |
|---|---|
| 操作 | 长对话后的继续提问，或从已保存会话恢复上下文 |
| 预期 | 近期问题能承接上下文，同时不要无限扩大单次输入 |
| 现象／边界例子 | 持久化内容能持续增长；机械全部注入会忽略请求预算，粗暴截字符串又可能混淆角色与顺序。这是实现难点，不宣称发生过某次上下文溢出事故 |
| 定位 | 宿主保存历史和适配器构造模型输入之间 |
| 调整 | 近期优先，只选择 user/assistant/tool 文本，限制正文字符数，选好后恢复原顺序 |
| 结果 | 选入正文长度有界，角色与先后关系保留；接受旧内容或单条文本前半段可能被舍弃 |

### 主动介绍

> 历史保存解决的是之后能不能查，模型上下文解决的是这一次应该看什么。我在 Claude 适配里把两者分开：从最近消息往前选择有效文本，保留角色，控制选入正文长度，再按原顺序交给模型。这样既能承接近期问题，也不会把所有历史无界地塞进去。代价是很早的背景可能被舍弃，所以我把它定位为有界历史桥接，而不是保证所有约束永久记住的长期记忆。

### 第一层追问：用长对话说明保留和舍弃

假设对话先谈一般背景，后来详细比较部署方式，最近才提出“只看本地方案”。当前策略优先保留最近内容，而不是只保留最早的一段。它没有理解哪条业务规则最重要，因此不能据此保证旧约束永不丢失。

已有测试提供了一个可以手算的小例子，预算为 12，按从旧到新排列：[测试][history-tests]

```text
user       1234567890
assistant  abcdefghij
tool       WXYZ
error      not context

选择后：assistant cdefghij + tool WXYZ
正文总长：8 + 4 = 12；旧 user 被舍弃，error 不进入这份历史。
```

| 追问类别 | 可以直接回答 |
|---|---|
| 架构：为什么放适配层？ | 不同后端接收历史的方式不同；宿主记录不是提供方原生会话，适配器应明确转换 |
| 实现：为什么反向选，最后正序输出？ | 反向选择让近期优先；最后恢复顺序，让模型仍按原来的先后读上下文 |
| 取舍：为什么不先做摘要？ | 当前采用简单、确定的选择规则，不增加一次摘要调用及新的信息丢失来源；这不是说摘要一定不好 |
| 失败：截断会切掉半句话吗？ | 会，当前可以保留某条消息的尾部，不保证句子或完整对话对齐；这是明确接受的限制 |
| 职责：能展示什么？ | 展示角色过滤、剩余预算、截取和拼接，再用上面的输入逐步推导结果 |

### 备查层与收口

`restoreTextHistory` 默认正文预算为 48,000，计数依据 JavaScript 字符串长度；不能称为精确 token 数。JSON 包装、当前问题、系统提示词与工具定义不在这份正文预算内。`promptWithHistory` 把历史作为带角色的引用数据，与当前问题分开；引用包装不是完全防注入保证。

Pi 初始化目前只回填 user/assistant，并未使用同样的桥接。被问“Pi 也这样吗”，直接回答“不完全一样”，不要为了叙事完整把两条适配路径合并。[Pi 初始化][pi-server]

**收口：**“我选的是近期优先、长度可控的方案，舍弃了对完整历史和语义重要性的保证。”

## 难点三：有答案，却不好回看取材依据

**面试主问：**“你为什么还做研究工具层，不是接个搜索工具就行了吗？”

**证据性质：**工具与网页读取实现、解析和拒绝条件测试定义。依据：[研究工具][research]、[网页适配][web]、[研究测试][research-tests]。

### 六项复盘

| 项目 | 内容 |
|---|---|
| 操作 | 查询公开资料、读取页面并形成比较结论 |
| 预期 | 不只得到一段答案，还能知道这次实际取得了什么材料 |
| 现象／边界例子 | 只有最终文字时不便还原取材；同一 URL 之后的网页内容也可能变化。这是需求与设计问题，不编造成已经发生的错引事故 |
| 定位 | 工具请求、工具返回和会话产物之间缺少明确对应 |
| 调整 | 保存查询或最终页面 URL、抓取时间和受限正文，再将观察交给模型 |
| 结果 | 可回看取材记录；不等于逐论点语义核验，也不是页面全文永久归档 |

### 主动介绍

> 我把研究工具的结果设计成两份输出：一份给模型继续分析，一份跟随会话保存。否则最终答案虽然存在，之后却不方便知道它依据了什么。现在检索或读取时会保存查询或页面地址、时间和取得的正文，便于回看与排查来源缺口。我解决的是取材过程可检查，不直接把来源留存等同于结论已经验证。

### 第一层追问与备查

| 追问类别 | 回答 |
|---|---|
| 架构：MCP 不能做吗？ | MCP 是能力连接方式；查询、时间和取材正文怎样成为本项目的产物，仍需要应用定义 |
| 实现：具体保存什么？ | 搜索产物保存 query、sources、fetchedAt、text；页面产物保存最终 url、fetchedAt、title、text，按各自结构说明，不说两者字段完全相同 |
| 取舍：为什么不完整存网页？ | 当前保留适合模型观察的受限文本，便于检查和控制规模；复杂渲染页面与完整归档不在这层已完成范围内 |
| 失败：没找到可读正文怎么办？ | 工具显式报错，不能生成一份伪装成取材成功的记录；答案应说明缺口，而不是补造来源 |
| 职责：自己实现了哪一层？ | 我实现参数约束、宿主执行及产物保存；搜索引擎本身、网页原内容不是我实现的 |

定位时按“收到的查询/URL → 返回正文与错误 → 是否保存产物 → 模型引用”检查。来源缺失不一定是模型问题，可能在工具解析或保存环节；这是诊断路线，不是新增的亲历事故。

只有被问到安全细节，才展开 `validatePublicUrl`、重定向复检、DNS 地址绑定与响应上限。已有测试检查私网和特殊地址、混合 DNS 结果、解析失败；本轮未重跑，也没有据此声称全面阻断提示注入。

**收口：**“现在能回看取材材料，结论与来源是否真正匹配还需要另一层判断。”

## 难点四：任务拆出去以后，规模和结果怎样收回来？

**面试主问：**“子 Agent 最难的是什么？”

**证据性质：**受限委派实现及并发、取消、部分失败、写盘失败测试定义。依据：[ResearchTools][research]、[研究回归][research-tests]。

### 六项复盘

| 项目 | 内容 |
|---|---|
| 操作 | 把确实独立的研究子问题委派出去 |
| 预期 | 有限规模地取材，并带回每个分支的结果 |
| 现象／异常输入 | 一个分支报错，另一分支成功；父任务取消时既有运行项也有排队项。这些有测试构造，不冒充真实供应商事故 |
| 定位 | 父子任务的预算作用域、状态记录和收尾关系 |
| 调整 | 运行时共享并发槽，父运行累计预算，子任务单独限制；结果按状态收集，取消分别处理等待与运行 |
| 结果 | 普通失败能与成功兄弟报告一起返回；写盘失败另行上报，不能笼统承诺所有失败均返回部分成功 |

### 主动介绍

> 子任务不难启动，难的是拆出去后还能控制总量并收回结果。我只对独立问题做可选委派，用父运行累计预算限制整个任务的扩张，再给各分支记录状态和报告。一个普通分支失败时，不把其他成功结果一起丢掉，而是把失败原因和成功内容分别交回来。这样父任务能看见哪些已经完成、哪些还缺证据，不需要把一个局部失败包装成全部成功或全部失败。

### 第一层追问与备查

| 追问类别 | 回答 |
|---|---|
| 架构：多开几个 Session 不一样吗？ | 这里有明确父子关系、父取消、共享预算和结果汇合；独立开会话本身不具备这些关系 |
| 实现：一个失败分支怎么表示？ | 用 ChildRecord 的 status、answer/error、sources 和产物位置记录；普通失败在 runChild 内转成失败报告 |
| 取舍：限制并发还不够吗？ | 并发限制同时多少，累计预算限制总共多少；前一批结束不应让本轮总预算清零 |
| 失败：写报告失败也能返回其他结果吗？ | 不保证。报告保存异常可使委派调用整体报错；allSettled 等待各 runChild 落定，finally 才负责清理和保存 |
| 职责：自己与 SDK 各管什么？ | 我管委派输入、预算、状态与收尾；子代理内部模型循环由 Pi SDK 执行 |

备查时再说具体上限：单运行时共享三个槽，一次委派一至三个子任务，同一父运行累计最多六个，父子共享二十四次网页工具调用预算；单子任务另限模型轮数和截止时间。网页工具调用计数不等于物理 HTTP 次数，也不等于费用封顶。

父取消与子任务截止时间组合成信号。排队项退出等待，运行项触发销毁，finally 释放槽并记录终态。当前截止时间从排队阶段也开始计算；超时在 ChildRecord 中归为 cancelled，并以错误文字区分父取消或子任务超时，不能另编一个不存在的 timeout 状态。

已有测试通过两个批次构造六个子任务，前三个启动后取消，检查排队项未继续启动、报告有终态；另有故意破坏报告目标的写盘失败用例。这里说的是测试设计，实际执行结果需要运行日志。Promise 等待也不能独立证明所有底层请求都停止或提供方立即停止计费。

**收口：**“我控制的是一次研究中的分支规模、状态和收尾，不是通用多机调度。”

## 难点五：调用入口统一了，为什么还要保留后端差异？

**面试主问：**“你做后端适配时，怎么避免上层充满 SDK 分支？”

**证据性质：**当前接口与装配实现；本节不把工厂可创建对象当成三家真实模型联调通过。依据：[后端工厂][factory]、[宿主装配][lifecycle]、[Pi 进程接口][pi-agent]。

### 六项复盘

| 项目 | 内容 |
|---|---|
| 操作 | 同一工作台接入不同后端 |
| 预期 | 上层通过公共入口发起调用、消费事件，不直接依赖每种 SDK |
| 现象／边界例子 | 可创建三种后端，并不意味着工具、历史、取消与鉴权完全等价。这是接入设计难点，不虚构某家 SDK 曾导致线上故障 |
| 定位 | 后端接口、适配器和真实宿主装配三层 |
| 调整 | 统一上层调用与生命周期接口，在适配器处理差异，并明确各后端已装配能力 |
| 结果 | 已适配后端可按配置选择；新增后端仍要实现适配，能力差异不会因接口统一自动消失 |

### 主动介绍

> 我不希望界面为每种 SDK 各写一套调用流程，所以在后端保留公共调用入口，由适配器处理具体实现。但我没有把“接口相同”讲成“能力相同”：比如研究工具主要装配在 Pi 路径，Claude 历史处理又是另外一条路径。上层因此少处理直接的 SDK 调用差异，而不是从此不需要关心功能是否受支持。

### 第一层追问与备查

| 追问类别 | 回答 |
|---|---|
| 架构：为什么不在 UI 直接调用？ | 将供应商调用和应用状态分开，避免每个界面都重复处理具体 SDK 生命周期 |
| 实现：公共入口是什么？ | AgentBackend.chat()；工厂按 provider 建立后端，宿主按当前能力装配工具 |
| 取舍：为什么不强行做到能力一样？ | 未实现的能力应明确暴露差异；伪装一致会让上层在运行时才发现不可用 |
| 失败：后端返回错误或异常结束呢？ | 要映射到上层能识别的事件和终态；统一错误形状不自动提供重试、补偿或成功保证 |
| 职责：自己实现了什么？ | 我复现实现适配接口及应用接线，不认领供应商模型或 SDK 内部执行循环 |

只有被问到进程时，再讲 Pi 通过 JSONL 子进程交换初始化、事件与工具请求，宿主代理执行所装配工具。模型 API Key 会传给执行 SDK 的子进程；不能把 Source 工具凭据的宿主处理扩大成“所有凭据从不离开宿主”。子进程也不是操作系统沙箱。

**收口：**“公共入口减少上层耦合，能力矩阵保留真实差异；我没有做自动按研究阶段切模型的路由。”

## 被问“有没有没达到预期的地方”，怎么讲

### 推荐回答：取材可回看，还不是研究质量闭环

> 当前工具和来源记录解决了过程可检查，但仅有 URL 不足以证明每条结论正确。因此我把成果限定为取材留存、分支状态和已保存内容，不直接报研究准确率。后续要补的是结论与来源的对应关系和有标准的质量检查，而不是继续增加几个工具名。现阶段可观察的结果是材料和失败能回看，接受的限制是最终判断仍需核验。

这是现有能力与目标的差距，不是说五点没有实现；依据是当前工具输出与来源保存方式。[实现][research]

### 备选回答：保存完整历史，不代表各后端恢复完全一致

> 宿主保存了历史，但后端实际接收什么还取决于适配器。Claude 有字符预算桥接，Pi 当前回填的角色和预算策略不同。所以我在接口统一之外保留这个差异，而不说所有后端无损恢复。后续对齐策略要分别检查入口，不能只改一份公共类型。

### 可以备用、不要抢主线的真实整改线索

项目[历史整改记录][review-record]提到过加密文件 magic 长度不一致，导致新实例不能读回凭据，并记录了跨实例回归。这可以作为“存储写入成功不等于跨实例读取成功”的备用案例；**本文未核对该项修复 diff，不补造字节偏移、当时日志或亲历定位顺序**。没有把细节讲清前，不主动用它替代任务状态主故事。

## 最后一次练习：把“我的决定”讲出来

回答“为什么这样设计”时，选一个实际决定，不罗列整套技术栈。例如：“受理必须先落记录再返回”“历史优先保留近期”“账号/运行标识不能靠文本猜”。然后交代一个可观察结果和一个接受的限制。

回答“你怎么定位的”时，用当前可复现的检查链说明：先重现输入，再看边界两侧的值或状态，缩小到具体处理层，最后比较调整前后的目标对象。没有原始排障记录时，说“我现在可以这样复现和核对”，不要伪造“我当时抓包两天才找到”。

回答“测试了没有”时，区分“代码里已有这个断言”“我本人跑过且有结果”“本文只给出待执行步骤”。只有第二种才能说“我运行后看到……通过”。记录至少包含：代码版本、输入、预期、实际输出、命令及结论；失败用例也应留下实际状态。

### 练习顺序与完成条件

| 练习 | 合格表现 |
|---|---|
| 任务生命周期，主动介绍 | 不看稿讲清受理、运行、保存和终态，没有把 accepted 当成功 |
| 任务生命周期，第一层追问 | 能拿一个重复提交例子解释两个标识，能回答保存失败怎么收口 |
| 上下文选择 | 能手算 12 字符例子，并承认截断、角色缺口与 Pi 差异 |
| 其余三点 | 每点能说一个输入、一个处理、一个结果，不靠名词撑满 |
| 反向检查 | 把“更稳定”“更安全”删掉以后，仍然能说清检查的对象 |

### 本文自审与验证范围

已按五条既有 Claim 核对叙事归属，检查主链/旁支、父累计预算、消息段语义、正常失败与写盘失败，以及“已有实现／待执行实验／后续方案”的时态。本文不改变 Claim 权限、不新增简历成果，也不宣称本轮运行了产品测试或独立多 Agent 评审。具体业务验收结果继续进入原有事实记录，不在口述稿中倒填。
