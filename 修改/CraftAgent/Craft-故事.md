**开场口述稿**

> ThreadCove 是我基于 Craft Agents 开源基座，围绕五个选点复现并实现的个人研究工作台。我想解决的是：技术调研除了最终答案，还需要知道资料来自哪里、哪些子问题完成了、中断后留下了什么。Pi 提出搜索、网页读取和可选委派请求，我在宿主实现工具执行、来源保存、并发与累计预算控制、取消及报告收集。不同 SDK 通过公共后端接口接入，Claude 路径单独做字符预算历史桥接。任务层区分受理和完成，用稳定消息 ID、快照和检查点保存内容，重启时标记未完成运行。五点共同让研究过程可检查、可约束，来源是否真正支持结论则需要额外核验。

面试时先讲主流程，再根据追问选择一个核心点深入；具体展示入口、短答和不会时的答法分别在 M4 与 M6。

## M2 · 为什么选择这个场景

### 一个贯穿全篇的例子

以下是**演示任务设计**，不是已经完成并留存验收报告的业务案例：

> 比较两个 Agent 框架，分别调查它们的工具扩展方式、运行与取消机制、部署约束，汇总差异并附上来源；查不到的部分明确留空。

这个例子适合当前项目，因为三个子问题可以独立取材，而且结果需要原始来源。它不要求先虚构金融数据接入、电商经营权限或企业知识库。

使用者输入问题后，Pi 后端可以选择 `web_search` 查找公开信息，再用 `web_fetch` 读取适合的 HTML/文本页面。对于确实独立的子问题，模型可调用 `delegate_research`。宿主建立子代理实例、约束工具与预算、保存各子任务状态和来源，再把结果交还父任务。最后的综合判断仍是模型生成内容；保留 URL 不等于结论必然正确。[E01、E02、E03]

### 为什么不是普通聊天页面

区别不在于宣称模型更聪明，而在于工程上管理了模型之外的对象：工具定义、执行入口、取材产物、子任务、状态和历史。只有界面而没有这些对象，失败很容易表现成“答案没出来”；有了显式对象，至少能区分没有来源、工具报错、子任务超时和任务取消。[E01、E03、E10]

也不是所有问题都需要 Agent。单个明确问题不应该无条件拆分；固定流程也可以由普通代码执行。这里让模型决定下一步取材动作，但把可用工具、扇出和执行预算交给宿主代码约束。复杂度来自研究路径的不确定，而不是为了使用“多 Agent”标签。[E01]

### 场景的当前不足

工作台已经有研究场景增量，不只是把通用 Source 接口改名成“研究”。但取材、委派和结果记录还不是完整研究质量闭环：当前未看到逐论点证据绑定、来源时效评分、冲突证据判定或研究质量基准。简历应突出已有工程链路，不把这些缺口写成已完成能力。[E01、E02、E04]

## M3 · 选型、架构与一条消息的旅程

### 选型怎么解释

下表是对现有实现的设计解释，不伪装成已经核实的个人决策时间线。

| 选型 | 在项目中的作用 | 为什么适合当前约束 | 不能顺带宣称的能力 |
|---|---|---|---|
| TypeScript / Bun 工作区 | 共享类型、应用代码和开发工具链 | 同一套工程组织后端、子进程和双端入口 | 工作区本身不会提高研究质量。 |
| Electron / React / Web 入口 | 展示会话、工具过程、状态与产物 | 让同一任务链有桌面和浏览器载体 | 不代表跨机器执行状态自动迁移。 |
| AgentBackend | 统一调用与生命周期接口 | 避免界面直接依赖每种 SDK | 接口统一不等于工具能力完全对等。 |
| Pi JSONL 子进程 | SDK 运行与宿主工具请求的进程接缝 | 依赖运行和工具执行职责可分别处理 | 不等于容器隔离或操作系统沙箱。 |
| Session / JSONL | 保存会话文本、结果与状态 | 当前是本地个人工作台，不必虚构数据库规模需求 | 没有跨进程事务或分布式 exactly-once 保证。 |
| MCP 与研究工具 | 外部能力调用和场景专用取材 | 框架接入能力与业务工具体分开建设 | 接入 MCP 不代表实现了 MCP 全部协议或已有完整 RAG。 |

技术版本以实际仓库的依赖与锁文件为准；旧施工规格中的锁版号不在简历里重复背诵。本轮没有独立安装这些依赖。[E07、E09、E12、E13]

### 架构分层

```text
Electron / Web 工作台
    │ 同一会话调用与事件消费入口
    ▼
SessionManager：受理、去重、忙碌检查、任务状态
    ├── AgentBackend：DeepSeek / Claude / Pi
    │       └── Pi JSONL 子进程：模型运行、工具请求
    │                │ 请求回宿主
    │                ▼
    │         有限工具面与宿主执行器
    │           ├── web_search / web_fetch → 带来源的取材产物
    │           ├── 已装配 MCP 代理工具
    │           └── delegate_research → 受限 Pi 叶子子代理
    │                                      └── 状态 / 来源 / 报告
    └── AgentEvent → RunTranscript → 会话文本、结果、错误
                            └── 稳定消息 ID / 累计快照 / 检查点
```

研究工具装配发生在 `createSession` 的 `provider === 'pi'` 分支。不能把这条图中的 Pi 专属能力画成所有后端都已具备。[E03]

### 请求受理不等于任务完成

UI 提交研究问题时带上 `requestId`。会话层先检查同一请求是否已经受理，以及会话是否忙碌；持久化用户消息和运行状态后，返回 `accepted/runId`。之后继续消费后端事件，文本、工具结果和错误进入记录。只有流正常完成、记录与终态保存成功，才发布完成信号。这样，RPC 返回、模型结束和任务成功不会混成一件事。[E03、E10]

这条链路提供本地去重和状态管理，不保证外部网络工具只执行一次。任务完成前断线，也不意味着后台工作立即停止；实际停止要经过取消链路。[E03]

## M4 · 五个技术故事，与简历逐条对应

### M4.1 研究工具接入与证据留存

研究任务需要的不只是正文，还要知道“从哪里取来的、什么时候取来的”。本项目把模型可见的 `web_search`、`web_fetch` 定义和宿主执行入口分开：工具给模型参数描述，真实请求由宿主处理；搜索与页面内容保存为会话目录中的 JSON 产物，带查询或 URL、`fetchedAt` 和正文。网页读取还包含公开地址检查、逐跳重定向复检、将已校验的 DNS 地址绑定到实际请求，以及响应与提取文本的大小限制。[E01、E02、E03]

这样做的价值是留下可检查的取材记录，而不是宣称“引用百分之百正确”。搜索文本中出现的 URL 只是来源线索；逐段结论是否受到证据支持，还需要额外的核验机制。网页被标记为不可信数据也只是防护的一部分，不能说从此杜绝提示注入。[E01、E02]

**面试展示物**：工具参数定义、一次搜索/页面产物的字段、URL 拦截测试。未取到真实运行产物时就展示源码和测试结构，不临时编造搜索结果。[E01、E04]

#### 30 秒摘要

> 我做技术调研时需要回看资料来源，所以为 Pi 研究路径实现了搜索、网页读取和宿主工具执行，把来源 URL、抓取时间及提取正文保存成会话产物。网页读取还校验地址、重定向和响应规模，交付的是可定位的取材记录，方便检查模型到底拿到了什么材料。

#### 90 秒讲法

> 这一点来自个人技术调研的需要。比如比较两个框架，只有模型的结论，很难追问它用了哪份资料、资料是什么时候获取的。我把目标定为让每次取材留下可回看的记录，于是在 Pi 分支接入 web_search、web_fetch 和 MCP 代理工具，把模型可见的工具参数与宿主执行入口分开。宿主搜索或读取网页后，将查询或 URL、抓取时间、正文保存为会话 JSON，再把观察结果交给模型。网页读取还会检查公开地址、绑定已校验的 DNS 地址，逐跳检查重定向，并限制响应大小和正文长度。这些限制使不合适的请求显式失败，也限定了每次观察的规模。我的交付物是工具契约、执行器和来源产物结构，可以顺着一次调用解释材料如何进入会话。不过有 URL 只能说明取材来源，结论是否真正受到资料支持还需要另一层核验。

#### 约 3 分钟讲法

> 我做个人技术调研时，希望比较结果能够回答“依据是什么”，而不仅是最后得到一段流畅文字。以比较两个框架的工具扩展和部署限制为例，搜索摘要可能只提供线索，真正判断还需要读取对应页面；如果过程没有留下材料，之后就很难区分没有找到资料、页面读取失败和模型忽略了资料。因此我把这一点的目标定为让模型取得公开材料，同时让宿主留下能够检查的取材记录。我在 Pi 研究路径中实现搜索、网页读取的参数定义与执行入口，并和已有 MCP 代理工具一起装配。模型负责提出查询或地址，宿主负责执行和保存，工具返回的观察则继续供模型选择下一步动作。搜索产物保存查询、来源列表、抓取时间和搜索文本；页面产物保存实际页面地址、抓取时间及受限正文，文件归入当前会话。这样就有了从工具请求到来源产物的具体对应关系，后面可以打开字段检查取材过程。网页读取还需要处理模型给出的地址可能不适合访问的问题。我实现公开地址校验，对解析结果进行检查，并把已校验地址绑定到实际连接；遇到重定向重新检查下一跳，避免只验证最初地址。响应时间、大小、类型和提取文本也受到限制，页面没有可读正文时就返回错误。这里的取舍是只取得受限文本，先保证接口清楚、产物可检查，没有把复杂页面渲染或全文证据评分加进同一个工具。代价是部分资料可能拿不到或者被截断，因此汇总时要留下缺口，不能把搜索线索当作已阅读全文。我可以展示工具定义、执行分支、保存字段和地址校验的测试结构，说明每个约束在哪一层生效。最终实现的是研究取材与来源留存；页面标注不可信并不消除所有提示注入，有来源记录也不代表每条结论已经完成证据核验，这两件事仍需要分别处理。

### M4.2 受限子 Agent 编排

一个较大的研究问题可能包含几个独立子问题，但无限递归委派会放大调用量，也会让取消和失败变得难以处理。我实现 `delegate_research`，为子问题建立独立 PiAgent 实例和工作目录；共享并发槽控制同一运行时的在途子任务，父运行累计子任务数与网页工具调用预算由父子共用。每个子任务另有模型轮数限制；网页计数不是物理 HTTP 请求数或费用封顶。子代理只获得叶子研究工具面，执行器拒绝再次委派。[E01]

取消与超时传递给子任务，各子任务的 finally 调用销毁、释放并发槽并保存终态。常规子任务失败被记录为失败报告，成功兄弟的报告仍可返回。报告保存失败时，`Promise.allSettled` 先等待各 runChild 落定，再把错误交回父调用；它不替代 finally 的清理，也不能单凭等待就证明底层进程或外部请求已经停止。[E01、E04]

当前是轻量、受限的委派机制，不是通用多 Agent DAG 平台。全局并发是**当前运行时实例内共享**，不是多进程或多机全局配额；独立目录与宿主白名单也不是 OS 安全沙箱。[E01]

**面试展示物**：ResearchSlots、ChildRecord、父取消/排队取消、失败分支保留和产物写失败用例。[E04]

#### 30 秒摘要

> 对可以独立调查的子问题，我实现了受限 Pi 子代理委派。宿主用共享并发槽、父运行累计任务与网页工具预算约束执行，子任务另有模型轮数和超时限制；同时传播取消，把各子任务的状态、来源和报告保存回父会话，保留可检查的分支结果。

#### 90 秒讲法

> 比较框架时，工具扩展、取消机制和部署限制可以独立取材，但如果只是让模型不断开新会话，调用量和失败收尾会很难控制。我因此实现 delegate_research，由父任务请求委派，宿主创建独立 Pi 子代理和工作目录，子代理只拿搜索与读取工具。运行时共享并发槽，同一个父运行累计限制子任务数和网页工具调用次数，每个子任务再单独限制模型轮数与截止时间。父任务取消时，排队和运行中的子任务沿各自路径退出，finally 调用销毁、释放槽和保存终态。普通模型错误会形成失败报告，成功兄弟的报告仍能一起返回；写盘失败则可能使委派调用整体报错，allSettled 先等各子调用落定。这形成了显式的父子控制流和报告产物。我的取舍是保留轻量叶子委派，不做一般依赖图；预算也不是跨机配额、物理网络次数或费用封顶。

#### 约 3 分钟讲法

> 这一点解决研究任务中“问题适合分开调查，但执行不能无限扩张”的矛盾。比如比较两个框架，工具扩展、取消机制和部署限制可以独立找资料，最后再汇总；如果问题本身相互依赖，就不应该为了并行而强拆。我的目标是让模型可以委派，同时把实际扇出、资源使用和收尾责任放在宿主。为此我实现 delegate_research，由父任务提出子问题，宿主为每项任务创建 PiAgent 和独立工作目录，建立包含标题、状态、回答、来源与产物位置的子任务记录。工具面只提供网页搜索和读取，执行器再检查是否允许委派，防止只靠提示词约束递归。预算分三个范围：同一运行时共享并发槽，一次委派限制提交数量，同一个父运行累计限制子任务总数和网页工具调用次数。父子复用同一份作用域，所以模型进入下一轮并不会重置累计预算；每个子任务的模型轮数和截止时间另外配置。这样既约束同时在途的工作，也约束整个父运行持续追加的工作。网页预算按工具入口计数，并不代表真实连接次数或者账单上限。失败处理则围绕记录的状态变化展开：先排队，拿到槽后运行，正常生成完整回答后完成；普通模型错误变成失败记录，父取消或截止时间触发取消记录。清理放在 finally 中调用销毁、释放槽并保存终态，报告和取材都由宿主写回父会话，独立工作目录不改变这个归属。如果一个子任务失败而兄弟成功，普通失败报告仍可以和成功结果一起返回；如果报告保存失败，委派可能整体报错，allSettled 会等待各子调用落定后再交回错误。它负责汇合，不能单独证明底层没有挂起。可以展示的产物是父子工具契约、预算作用域、子任务记录和失败分支；取舍是轻量可控的叶子编排，暂不增加通用依赖调度或自动重规划，也不把目录隔离称为操作系统沙箱。

### M4.3 Context Engineering

本条桥接已确认在 ClaudeAgent 的 restoreHistory/chatImpl 中被调用，不能泛称 Pi 研究主链也相同。[E14、E15]

历史记录可以持久化，但模型并不会自动理解宿主保存的全部会话。这里单独处理“存了什么”和“本次给模型什么”：`restoreTextHistory` 从新到旧选择 user、assistant、tool 消息，按字符预算截取，再恢复原顺序；`promptWithHistory` 将角色和正文编码为引用式 JSON 历史，并与当前问题分开。这样能恢复有限文本上下文，而不是每次无限注入整段日志。[E05]

取舍是保留近期上下文、控制实现复杂度，同时接受较旧信息可能被丢弃、单条消息可能被截断。代码预算是 JavaScript 字符串长度，不是 tokenizer 计数，也不是包含系统提示词、工具定义与当前问题的完整请求预算。没有摘要算法、语义检索或长期记忆层，就不应写成“智能 Memory 系统”。[E05、E06]

Pi 当前把 user/assistant 历史填回内存 Session，没有在该路径使用相同字符预算，也没有回填 tool 文本。这是当前上下文策略的真实不一致，作为后续改进项保留，不在本轮改业务代码。[E15]

**面试展示物**：角色过滤、预算内保留最新内容及不透明标记的回归测试。引用式包装不是对恶意历史内容的绝对隔离。[E06]

#### 30 秒摘要

> Claude 路径中，历史存下来后还要决定下一次给模型什么。我实现按字符预算选择近期 user、assistant、tool 文本，保留角色和顺序，再以引用历史拼接当前问题，得到有界文本输入。这是工作台的 Claude 适配能力，与 Pi 研究路径的历史回填分开。

#### 90 秒讲法

> 多后端工作台保存了会话，不代表每个 SDK 都能直接理解全部记录。我在 Claude 路径里处理的是后续提问的历史输入：既要带上最近的有效对话，又不能把整段执行日志无界塞入请求。我实现 restoreTextHistory，从新到旧选择 user、assistant、tool 文本，按剩余字符预算截取，再恢复时间顺序；promptWithHistory 将角色与正文包装成引用式 JSON，当前问题单独放在后面。可检查的产物是选出的历史片段和最终输入结构。取舍是使用简单确定的近期优先策略，旧约束可能被丢弃，单条消息也可能被截断；字符预算还不包含包装、系统提示和当前问题，所以不是完整 token 预算。Pi 当前只回填 user/assistant，未对齐这套预算与工具文本，因此我把 Claude 历史桥接作为单独能力讲，不把它说成研究主链的统一记忆阶段。

#### 约 3 分钟讲法

> 我在多后端研究工作台里遇到的设计问题是，宿主保存会话和模型理解历史并不是同一个步骤。比如用户在讨论一个框架后继续追问部署约束，模型需要知道最近谈了什么，但会话记录里还可能包含工具结果和错误事件，不能不加选择地全部放进下一次请求。我围绕 Claude 后端实现文本历史桥接，目标是在后续提问中保留近期有效信息，同时给历史正文一个明确上限。我把这件事拆成选择和组装两部分：选择函数从最新消息向前遍历，只取 user、assistant、tool 的文本，按剩余字符预算保留内容；完成选择后再恢复原来的时间顺序，避免倒着给模型讲对话。组装函数把角色和正文编码成引用式历史，当前问题单独放在后面，让输入结构能够区分过去的材料与本次任务。这样可以逐步展示原始消息、被选中的片段以及最终拼接结果，而不是笼统地说“恢复了上下文”。这里最主要的取舍是近期优先和确定性。我没有加入摘要模型或语义检索，代码行为容易解释，但较旧的约束可能被丢弃，预算不足时也可能只保留某条消息的末尾。如果用户重要要求恰好落在被截断的位置，回答就可能受影响，因此不能把它称作无损记忆。预算使用 JavaScript 字符串长度，约束的是历史正文；引用包装、系统提示、工具定义和当前问题都不在这一项计数中，不同语言的 token 数也不会相同。因此它不能直接代表完整请求容量或费用。另一个需要讲清的边界是后端差异：Claude 实际调用了这两个函数，Pi 当前则把 user/assistant 历史回填到内存会话，并没有同样的工具文本和字符预算。我的交付物是 Claude 路径可定位的历史选择、截取和拼接逻辑，以及能够检查这些规则的用例定义；后续可以对齐其他后端，但当前不把局部桥接扩展成全后端长期语义记忆，也不把引用包装说成绝对的提示注入隔离。

### M4.4 多后端适配与进程边界

模型服务和 SDK 的运行方式不同，统一的应该是上层如何调用，而不是假装底层能力完全相同。工厂按 provider 配置实例化 DeepSeek、Claude 或 Pi；UI 与会话层面对公共调用和生命周期接口。Pi 通过子进程运行 SDK，使用 JSONL 交换消息与事件，工具执行请求代理回宿主。[E07、E09]

这样可以在已有后端之间按配置切换，但不是自动根据研究步骤选择模型。当前研究工具是在 Pi 路径里明确装配的；工厂能创建 Claude 后端，不代表 Claude 的研究工具闭环也已联调完成。源码注释里“凭据留在宿主”应严格限定到宿主代为执行的 Source 工具凭据；模型 API Key 在初始化消息中进入 Pi 子进程，不能误说“子进程没有任何密钥”。[E03、E09]

**面试展示物**：工厂映射、init/event/tool 请求与结果契约、Pi 子进程启动代码。工厂用例检查路由和接口表面，不能据此证明真实模型能力与调用质量。[E08]

#### 30 秒摘要

> 为让同一工作台接入不同 SDK，我实现公共后端调用与生命周期接口，按配置选择 DeepSeek、Claude 或 Pi。Pi SDK 通过 JSONL 子进程运行，工具请求带关联标识回到宿主执行，再返回结果，形成可检查的后端适配与工具往返契约。

#### 90 秒讲法

> 工作台接入多个模型后，如果会话层直接跟随每个 SDK 的初始化和流式类型变化，工具执行与状态处理就会散落在不同分支。我因此复现并实现 AgentBackend 的公共调用和生命周期入口，由工厂按 provider 配置建立已有后端，让会话层复用同一套消费方式。Pi 的接入还涉及运行方式差异，我把 SDK 放在 JSONL 子进程中，宿主发送初始化配置，子进程返回就绪和事件；工具执行请求带关联标识回到宿主，执行结果再传回去。能展示的产物是工厂映射、消息契约、子进程入口及工具往返路径。统一接口的代价是仍要维护具体适配器，不能假装各后端功能完全相同。研究工具目前只装配在 Pi 路径，模型 API Key 也需要进入 SDK 子进程，因此这属于调用与进程职责的划分，不是自动模型路由或所有凭据都留在宿主的安全沙箱。

#### 约 3 分钟讲法

> 这一点服务于同一研究工作台接入不同模型和 SDK 的需求。上层关心的是提交问题、接收文本或工具事件、取消运行和保存结果，但不同后端的初始化方式与消息类型不同；如果直接把这些差异铺到会话层和界面，后面新增一种后端时就需要到多个位置改动。我的目标是把调用方式稳定在应用边界内，同时保留各后端真实的能力差异。我复现并实现公共后端接口及工厂，根据 provider 配置建立 DeepSeek、Claude 或 Pi，让会话层通过相同入口调用并消费适配后的事件。这个统一主要针对调用和生命周期，不是把所有 SDK 变成相同产品。Pi 的运行方式还需要单独处理：我把 SDK 放入子进程，通过标准输入输出交换 JSONL 消息。宿主负责启动与初始化，子进程接收配置并返回就绪或事件；模型提出工具请求后，消息带着关联标识回到宿主，宿主执行器完成操作再把对应结果传回去，模型才能沿这次调用继续处理。这样可以沿一次工具往返展示请求从哪里发出、谁执行、结果如何对应，以及事件怎样进入公共消费者。具体交付物是工厂映射、适配器、初始化和工具消息契约以及宿主集成路径。失败时也要按边界定位：配置不支持属于工厂问题，子进程未就绪属于初始化问题，宿主执行工具失败则是另一条返回路径，不能都归结为模型没有回答。设计上的取舍是用一层适配和一个进程接缝换取调用职责清楚，相应地也要维护协议、退出与错误处理。统一入口不代表所有后端已具备同一套工具和历史恢复；研究工具当前在 Pi 分支装配，Claude 的历史桥接又是单独策略。进程边界同样不等于安全沙箱：宿主管理工具执行并不意味着所有凭据都停留在宿主，模型 API Key 会随初始化进入 SDK 所在子进程。我可以据此讲清应用层实现与第三方 SDK 的分工，展示路由和工具契约，而不同提供方的真实联调效果要看各自运行记录。

### M4.5 任务生命周期与流式恢复

任务执行中最容易讲混的是“页面恢复了”和“工作重新执行了”。`RunTranscript` 为文本段分配稳定消息 ID；增量事件附带累计快照，完成文本更新同一条消息而不是简单追加另一条；文本、工具结果与错误按事件或检查点节奏写入会话记录。会话层另外维护 runId 和终态，重启时把没有结束的 running 标记为 interrupted。[E03、E10]

当前恢复的是已保存内容和可解释的状态，重启时不主动重新发起旧任务的模型或网络调用。已经发出的请求如何执行和计费取决于提供方，不能由本地中断标记推定。检查点之间仍可能丢失尾部内容，累计快照也会增加长回复的传输量。[E10、E12]

**面试展示物**：submitMessage 的受理/完成分离、RunTranscript 的稳定 ID 更新、错误保存与 interrupted 逻辑。事件 parity 测试在测试文件内部镜像两套映射，不能独自证明真实 UI 与运行时端到端无漂移。[E11]

#### 30 秒摘要

> 为区分提交成功、模型运行和最终结果，我实现 requestId 受理去重与 runId 运行标识，通过稳定消息 ID、累计文本快照和检查点保存已有输出。重启恢复读取落盘内容并把残留运行标记为中断，交付的是可检查的内容与状态，不会主动重放旧任务。

#### 90 秒讲法

> 研究任务运行较久，页面请求返回、模型完成和结果保存不能混为一件事，否则重复点击或断线后很难判断该不该重试。我在会话层实现受理与终态分离：requestId 用于同一请求去重，受理时保存用户消息和 running 状态，再返回 accepted/runId；之后继续消费后端事件，最终根据完成与落盘情况处理终态。文本记录由 RunTranscript 管理，同一文本段使用稳定消息 ID，增量携带累计快照，完成文本更新原记录，检查点保存已有内容。这样可以展示一条消息如何从受理、更新走到结束，也为恢复显示提供依据。代价是快照带来传输开销，检查点之间仍可能丢失尾部。重启时只读回已存内容并标记 interrupted，不主动重放旧模型或网络调用；外部请求是否继续执行或结算不能从本地状态推定，实际界面效果还需要真实消费路径验证。

#### 约 3 分钟讲法

> 这一点围绕长时间研究任务的状态识别展开。用户提交问题后，网络请求可能已经返回，模型却还在取材；如果此时断线或者再次点击提交，单靠页面是否收到响应无法判断任务有没有受理、有没有完成，也无法知道此前生成的内容保存了多少。我的目标是把这些时刻分开，并为中断后的回看留下具体记录。我在会话层实现请求受理与运行终态分离：提交携带 requestId，先检查请求去重和会话是否忙碌，保存用户消息与 running 状态，再返回 accepted 和本次 runId。这里的受理只是说明工作进入处理流程，后端事件仍继续消费，只有运行、记录刷新和终态处理满足条件后才发布相应完成结果。两个标识用于关联请求和运行，并不保证外部工具只执行一次。对于流式文本，我实现 RunTranscript 的记录消费，让同一个文本段有稳定消息 ID；增量事件更新该段并携带累计快照，完成文本则替换同一段，持久化也按这个标识更新。这样恢复显示有可以对齐的对象，而不是把每个增量或完成事件都当作一条新消息盲目追加。文本、工具结果和错误按事件或检查点写入会话，形成可以检查的落盘内容。失败路径也要明确：后端没有完成事件、出现错误、取消或终态保存失败，都不能因为已经生成部分文字就判断成功。应用重启后读取已保存记录，把残留运行和未结束子报告标记为中断，供用户回看已有内容，而不主动重新发起旧任务的模型或网络调用。这个取舍让恢复行为更容易解释，但检查点之间可能丢失尾部，累计快照会增加长回复的传输和存储开销；已经发送给提供方的请求如何执行或计费，也不由本地标记决定。我能展示受理返回、运行标识、文本更新、检查点和中断状态这些产物及控制分支。实际界面是否正确消费快照需要走真实应用路径，字段镜像用例不能替代这层验证，因此我把当前成果明确为运行状态管理与内容恢复基础，而不是无损事件回放或自动续跑。

## M5 · 演进逻辑与验证：不把施工顺序说成真实经历

旧材料的后端、会话、来源接入、传输和事件仍是基础。当前五点以个人研究场景组织：主故事围绕 **Pi 的取材、可选委派和执行记录** 展开，后端适配提供共同入口，**Claude 有界历史桥接是另一条能力线**。五个选点构成能力组合，不是每次请求依次通过的五个阶段。

可以按以下依赖解释设计顺序：先有后端和事件契约，工具才能返回统一结果；有会话和宿主工具边界，才能控制研究产物归属；有取消和预算，再增加子代理；最后由 UI 消费同一任务状态。这是便于说明架构的顺序，不是已经核实的个人开发日程。[E01、E03、E07、E10]

验证分成三层。源码检查能证明机制存在；测试定义说明已经准备了哪些断言；实际运行报告才证明特定版本在特定环境通过。仓库文档记载了 2026-09-14 的测试和 Pi SDK 联调，但不能把那天的结果自动推广到当前全部研究功能。本轮只完成源码/测试定义核对和简历材料校验，未运行程序测试或真实 API。[E04、E06、E08、E11、E12]

## M6 · 失败场景与八轮二层追问

### 场景一：父任务取消时，有的子任务正在运行，有的还在排队

不要只回答“调用 AbortController”。真正要回答的是：排队任务是否会继续拿到槽，运行任务是否停止，释放动作是否重复，最终报告是否留下一个永远 running 的状态。当前实现把父取消与子任务截止时间组合，排队等待可取消，运行中的子代理收到销毁调用，finally 中释放槽并保存 cancelled/failed 等终态。对应测试定义构造运行与排队并存的情况，检查没有额外子任务在取消后继续启动。[E01、E04]

这是已有代码和测试场景，不能包装成“线上某次事故造成损失，我连夜修好了”。演示失败恢复时应展示测试输入与断言。

### 场景二：一个子任务结果不错，但另一个子任务报告写盘失败

普通模型调用失败形成失败报告，父调用仍能获得成功兄弟的结果；报告持久化失败可能让委派调用整体报错。`allSettled` 等待各 runChild 落定再交回错误，各子任务通过 finally 调用销毁、释放槽并保存终态。等待汇合不保证底层永不挂起或外部请求已经停止。对应测试定义通过破坏一个报告目的路径注入写失败，并检查兄弟任务清理情况。[E01、E04]

正确的恢复说明是“保留已经落下的产物，明确当前调用失败原因”，不是“所有结果一定成功返回”。

| 一个子任务失败会怎样？→ 写盘失败也一样吗？ | 普通失败留下失败报告，写盘失败可能让委派整体报错。 | 解释 catch、finally 与 allSettled 各自职责，并区分成功兄弟报告与父调用返回。见 Q02.3。 | 底层退出是否挂起需运行记录，我先限定到已定位的清理控制流。 |
| 字符预算解决什么？→ Pi 也一样吗？ | 限定 Claude 本次历史正文，Pi 回填路径不同。 | 最近消息、角色过滤、截取和顺序恢复；说明包装和当前问题不计入正文预算。见 Q03.1–Q03.3。 | 无法手算 token 时就按字符解释，不声称精确 token 预算或长期记忆。 |
| 重启能继续吗？→ 会不会重复外部请求或继续计费？ | 恢复已存内容并标记中断，不主动重放旧调用。 | 对照 requestId/runId、快照和终态；已发出请求的执行与结算由提供方决定。见 Q05.1–Q05.3。 | 没有提供方记录时不判断计费，当前可展示的是本地恢复逻辑与记录。 |
| 哪些是你实现的？→ 如何知道行为正确，SDK 和 AI 各做了什么？ | 我围绕五点复现实现应用层能力，SDK 提供模型循环。 | 任选工具契约、预算或文本消费者解释本人实现；把实现、测试定义、实际输出分开，AI 辅助据实说明。见 QA 共用问题。 | 我会明确能解释的接口和仍需核对的细节；未有运行记录的效果不写成已经通过。 |

## M7 · 项目边界与后续优先级

**现在可以讲**：研究专用工具及来源产物、宿主工具面、受限 Pi 子代理、Claude 字符预算历史桥接、已有后端配置切换、任务生命周期和流式检查点。

**现在不能讲**：三个后端研究能力完全一致；全自动阶段模型路由；通用多 Agent 调度平台；完整 SDK resume；长期语义记忆；完整研究质量 Benchmark；所有事件可重放；全链路防注入；所有凭据不进入子进程；全量测试在本次全部通过。[E01—E15]

下一阶段应先对齐 Pi 研究路径的历史预算与工具记录回填，并补**当前研究路径的可重复端到端验收记录**，再考虑研究质量评估：给出固定问题、来源、工具轨迹、报告和失败对照，明确模型调用成本与环境。之后再建立小型正例/反例/模糊例集合，测试来源过时、证据冲突和引用不支持结论的情况。这是后续设计，不写进现有简历成果。

与 Clawtide 的能力互补是：ThreadCove 侧重研究取材、受限委派、上下文与运行记录，Clawtide 侧重消息或计划入口、配置和资源归属。这连接的是工程能力，不推断共享实现或开发先后因果。

## M8 · 展开口述稿与术语速查

### 展开口述稿

> ThreadCove 的场景是个人技术研究，输入通常是一个要比较或调查的问题。这个场景的难点不只是让模型生成答案，而是研究过程中资料从哪里来、哪些子问题可以分开做、执行失败后还剩下什么。
>
> 我把项目分成模型调用和宿主管理两部分。模型可以请求搜索、读取网页，或者把独立子问题委派出去；宿主决定它实际拥有的工具、能用多少资源，以及何时停止。当前研究路径接在 Pi 后端，MCP 代理工具和研究工具都通过宿主执行入口接入。每次取材保存来源和时间，所以后面可以回看依据，但我不会把“有 URL”当成“结论已经验证”。
>
> 子代理部分由宿主控制。我用运行时共享并发槽、父运行累计子任务与网页工具调用预算限制扇出，子任务的模型轮数单独约束；父取消和子任务超时传入清理流程，状态与报告由宿主保存。普通子任务失败可以与成功结果一起返回，报告保存失败则等待各子调用落定后报错。
>
> 上下文也需要单独管理。Claude 适配路径按字符预算取最近的有效历史，保留角色和顺序，并与当前问题分开；Pi 研究路径目前使用另一套 user/assistant 回填，预算和工具历史尚未对齐。我会把这两条路径分开讲，不把局部文本桥接夸大为全后端长期记忆。
>
> 工程层用 AgentBackend 把后端接口统一起来，Pi SDK 放在 JSONL 子进程里；任务层区分请求受理和真正完成，用稳定消息 ID、累计快照和检查点保存进度。重启后能恢复已保存文本并标记中断，不会自动重放付费调用。
>
> 当前项目最有价值的是可检查、可约束的研究执行链。研究质量评估和跨后端工具能力对齐仍需补充，我不会把这些计划当成已经交付的结果。

### 容易混淆的术语

| 术语 | 本项目中的准确含义 |
|---|---|
| Harness | 给模型组织工具、上下文与执行交互的应用层；不是所有执行隔离措施的总称。 |
| Runtime | 本项目实际执行所处的进程、宿主和生命周期边界；不能凭一个接口就称完整 Runtime 平台。 |
| Session / Workspace | Session 管会话与任务记录；Workspace 管所属环境、来源和偏好，可容纳多个 Session。 |
| Source / Tool / Skill | Source 偏连接与配置；Tool 是模型可调用能力；Skill 是使用方式或步骤的指令材料。目录内用于写简历的 Skill 不等于项目运行时新增功能。 |
| delegate_research | 受约束的叶子研究子代理委派，不是通用多 Agent DAG。 |
| 历史恢复 | 宿主保存文本的有限注入；不等同于 provider 原生 session resume。 |
| AgentEvent | 事件形状与消费契约；持久化、重试和回放需要另外实现。 |
| 来源产物 | 带 URL/时间/正文的取材记录；不等同于逐论点验证完成的证据链。 |
| 回归测试 / Agent Eval | 前者可检查预算、取消和字段；后者还要检验任务与研究结论质量，当前不能混为一谈。 |
