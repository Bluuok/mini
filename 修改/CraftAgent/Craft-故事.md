> 这个项目叫 ThreadCove，是我围绕个人技术调研做的研究 Agent 工作台，架构参考了 Craft Agents。我关注的不是把聊天窗口换个皮肤，而是把研究过程变成可以检查和控制的执行链：模型通过工具检索和读取网页，来源和抓取时间跟随结果保存；适合拆开的子问题可以交给受限的 Pi 子代理，宿主负责并发、预算、取消和结果收集；任务中断以后，工作台保留已有文本和执行状态。我的介绍会重点讲工具面、上下文、子任务边界和恢复机制，不把它说成企业级研究平台，也不把接入 SDK 说成自研模型。

## M2 · 为什么选择这个场景

### 一个贯穿全篇的例子

以下是**演示任务设计**，不是已经完成并留存验收报告的业务案例：

> 比较两个 Agent 框架，分别调查它们的工具扩展方式、运行与取消机制、部署约束，汇总差异并附上来源；查不到的部分明确留空。

这个例子适合当前项目，因为三个子问题可以独立取材，而且结果需要原始来源。它不要求先虚构金融数据接入、电商经营权限或企业知识库。

使用者输入问题后，Pi 后端可以选择 `web_search` 查找公开信息，再用 `web_fetch` 读取适合的 HTML/文本页面。对于确实独立的子问题，模型可调用 `delegate_research`。宿主建立子代理实例、约束工具与预算、保存各子任务状态和来源，再把结果交还父任务。最后的综合判断仍是模型生成内容；保留 URL 不等于结论必然正确。[E01、E02、E03]

### 为什么不是普通聊天页面

区别不在于宣称模型更聪明，而在于工程上管理了模型之外的对象：工具定义、执行入口、取材产物、子任务、状态和历史。只有界面而没有这些对象，失败很容易表现成“答案没出来”；有了显式对象，至少能区分没有来源、工具报错、子任务超时和任务取消。[E01、E03、E10]

也不是所有问题都需要 Agent。单个明确问题不应该无条件拆分；固定流程也可以由普通代码执行。这里让模型决定下一步取材动作，但把可用工具、扇出和执行预算交给宿主代码约束。复杂度来自研究路径的不确定，而不是为了使用“多 Agent”标签。[E01]

### 场景的当前不足

工作台已经有研究场景增量，不只是把通用 Source 接口改名成“研究”。但取材、委派和结果记录还不是完整研究质量闭环：当前未看到逐论点证据绑定、来源时效评分、冲突证据判定或研究质量基准。简历应突出已有工程链路，不把这些缺口写成已完成能力。[E01、E02、E04]

## M3 · 选型、架构与一条消息的旅程

### 选型怎么解释

下表是对现有实现的设计解释，不伪装成已经核实的个人决策时间线。

| 选型 | 在项目中的作用 | 为什么适合当前约束 | 不能顺带宣称的能力 |
|---|---|---|---|
| TypeScript / Bun 工作区 | 共享类型、应用代码和开发工具链 | 同一套工程组织后端、子进程和双端入口 | 工作区本身不会提高研究质量。 |
| Electron / React / Web 入口 | 展示会话、工具过程、状态与产物 | 让同一任务链有桌面和浏览器载体 | 不代表跨机器执行状态自动迁移。 |
| AgentBackend | 统一调用与生命周期接口 | 避免界面直接依赖每种 SDK | 接口统一不等于工具能力完全对等。 |
| Pi JSONL 子进程 | SDK 运行与宿主工具请求的进程接缝 | 依赖运行和工具执行职责可分别处理 | 不等于容器隔离或操作系统沙箱。 |
| Session / JSONL | 保存会话文本、结果与状态 | 当前是本地个人工作台，不必虚构数据库规模需求 | 没有跨进程事务或分布式 exactly-once 保证。 |
| MCP 与研究工具 | 外部能力调用和场景专用取材 | 框架接入能力与业务工具体分开建设 | 接入 MCP 不代表实现了 MCP 全部协议或已有完整 RAG。 |

技术版本以实际仓库的依赖与锁文件为准；旧施工规格中的锁版号不在简历里重复背诵。本轮没有独立安装这些依赖。[E07、E09、E12、E13]

### 架构分层

```text
Electron / Web 工作台
    │ 同一会话调用与事件消费入口
    ▼
SessionManager：受理、去重、忙碌检查、任务状态
    ├── AgentBackend：DeepSeek / Claude / Pi
    │       └── Pi JSONL 子进程：模型运行、工具请求
    │                │ 请求回宿主
    │                ▼
    │         有限工具面与宿主执行器
    │           ├── web_search / web_fetch → 带来源的取材产物
    │           ├── 已装配 MCP 代理工具
    │           └── delegate_research → 受限 Pi 叶子子代理
    │                                      └── 状态 / 来源 / 报告
    └── AgentEvent → RunTranscript → 会话文本、结果、错误
                            └── 稳定消息 ID / 累计快照 / 检查点
```

研究工具装配发生在 `createSession` 的 `provider === 'pi'` 分支。不能把这条图中的 Pi 专属能力画成所有后端都已具备。[E03]

### 请求受理不等于任务完成

UI 提交研究问题时带上 `requestId`。会话层先检查同一请求是否已经受理，以及会话是否忙碌；持久化用户消息和运行状态后，返回 `accepted/runId`。之后继续消费后端事件，文本、工具结果和错误进入记录。只有流正常完成、记录与终态保存成功，才发布完成信号。这样，RPC 返回、模型结束和任务成功不会混成一件事。[E03、E10]

这条链路提供本地去重和状态管理，不保证外部网络工具只执行一次。任务完成前断线，也不意味着后台工作立即停止；实际停止要经过取消链路。[E03]

## M4 · 五个技术故事，与简历逐条对应

### M4.1 研究工具接入与证据留存

研究任务需要的不只是正文，还要知道“从哪里取来的、什么时候取来的”。本项目把模型可见的 `web_search`、`web_fetch` 定义和宿主执行入口分开：工具给模型参数描述，真实请求由宿主处理；搜索与页面内容保存为会话目录中的 JSON 产物，带查询或 URL、`fetchedAt` 和正文。网页读取还包含公开地址检查、逐跳重定向复检、将已校验的 DNS 地址绑定到实际请求，以及响应与提取文本的大小限制。[E01、E02、E03]

这样做的价值是留下可检查的取材记录，而不是宣称“引用百分之百正确”。搜索文本中出现的 URL 只是来源线索；逐段结论是否受到证据支持，还需要额外的核验机制。网页被标记为不可信数据也只是防护的一部分，不能说从此杜绝提示注入。[E01、E02]

**面试展示物**：工具参数定义、一次搜索/页面产物的字段、URL 拦截测试。未取到真实运行产物时就展示源码和测试结构，不临时编造搜索结果。[E01、E04]

### M4.2 受限子 Agent 编排

一个较大的研究问题可能包含几个独立子问题，但无限递归委派会放大调用量，也会让取消和失败变得难以处理。`delegate_research` 为子问题建立独立 PiAgent 实例和工作目录；共享并发槽控制同一运行时的在途子任务，父运行共享子任务数与网页请求预算。子代理只获得叶子研究工具面，执行器还会拒绝再次委派，限制不只写在提示词里。[E01]

取消与超时会传递给子任务；清理时销毁子代理、释放并发槽并保存终态。常规子任务失败被记录为失败报告，不直接吞掉兄弟任务的成功结果。`Promise.allSettled` 的另一个作用是：即使某个报告保存失败，也等待其他任务结束清理，再把错误交回父调用。[E01、E04]

当前是轻量、受限的委派机制，不是通用多 Agent DAG 平台。全局并发是**当前运行时实例内共享**，不是多进程或多机全局配额；独立目录与宿主白名单也不是 OS 安全沙箱。[E01]

**面试展示物**：ResearchSlots、ChildRecord、父取消/排队取消、失败分支保留和产物写失败用例。[E04]

### M4.3 Context Engineering

本条桥接已确认在 ClaudeAgent 的 restoreHistory/chatImpl 中被调用，不能泛称 Pi 研究主链也相同。[E14、E15]

历史记录可以持久化，但模型并不会自动理解宿主保存的全部会话。这里单独处理“存了什么”和“本次给模型什么”：`restoreTextHistory` 从新到旧选择 user、assistant、tool 消息，按字符预算截取，再恢复原顺序；`promptWithHistory` 将角色和正文编码为引用式 JSON 历史，并与当前问题分开。这样能恢复有限文本上下文，而不是每次无限注入整段日志。[E05]

取舍是保留近期上下文、控制实现复杂度，同时接受较旧信息可能被丢弃、单条消息可能被截断。代码预算是 JavaScript 字符串长度，不是 tokenizer 计数，也不是包含系统提示词、工具定义与当前问题的完整请求预算。没有摘要算法、语义检索或长期记忆层，就不应写成“智能 Memory 系统”。[E05、E06]

Pi 当前把 user/assistant 历史填回内存 Session，没有在该路径使用相同字符预算，也没有回填 tool 文本。这是当前上下文策略的真实不一致，作为后续改进项保留，不在本轮改业务代码。[E15]

**面试展示物**：角色过滤、预算内保留最新内容及不透明标记的回归测试。引用式包装不是对恶意历史内容的绝对隔离。[E06]

### M4.4 多后端适配与进程边界

模型服务和 SDK 的运行方式不同，统一的应该是上层如何调用，而不是假装底层能力完全相同。工厂按 provider 配置实例化 DeepSeek、Claude 或 Pi；UI 与会话层面对公共调用和生命周期接口。Pi 通过子进程运行 SDK，使用 JSONL 交换消息与事件，工具执行请求代理回宿主。[E07、E09]

这样可以在已有后端之间按配置切换，但不是自动根据研究步骤选择模型。当前研究工具是在 Pi 路径里明确装配的；工厂能创建 Claude 后端，不代表 Claude 的研究工具闭环也已联调完成。源码注释里“凭据留在宿主”应严格限定到宿主代为执行的 Source 工具凭据；模型 API Key 在初始化消息中进入 Pi 子进程，不能误说“子进程没有任何密钥”。[E03、E09]

**面试展示物**：工厂映射、init/event/tool 请求与结果契约、Pi 子进程启动代码。工厂测试证明路由和接口表面，不证明真实模型能力与调用质量。[E08]

### M4.5 任务生命周期与流式恢复

任务执行中最容易讲混的是“页面恢复了”和“工作重新执行了”。`RunTranscript` 为文本段分配稳定消息 ID；增量事件附带累计快照，完成文本更新同一条消息而不是简单追加另一条；文本、工具结果与错误按事件或检查点节奏写入会话记录。会话层另外维护 runId 和终态，重启时把没有结束的 running 标记为 interrupted。[E03、E10]

因此当前恢复的是已经保存的内容和可解释的状态，不会在重启时自动重放未完成的网络请求或继续产生费用。检查点之间仍可能丢失一段尾部内容，累计快照也会增加长回复的传输量。这些代价比泛称“实时恢复、零丢失”更适合在面试中说明。[E10、E12]

**面试展示物**：submitMessage 的受理/完成分离、RunTranscript 的稳定 ID 更新、错误保存与 interrupted 逻辑。事件 parity 测试在测试文件内部镜像两套映射，不能独自证明真实 UI 与运行时端到端无漂移。[E11]

## M5 · 演进逻辑与验证：不把施工顺序说成真实经历

旧材料的五点是后端、会话、来源接入、传输和事件，它们仍是基础，但不应限制当前源码已经存在的研究能力。新版不是凭空增加一个热门标签，而是把原本偏平台的讲法调整为：**研究工具 → 有界上下文与受限委派 → 执行边界 → 可检查的状态和记录**。

可以按以下依赖解释设计顺序：先有后端和事件契约，工具才能返回统一结果；有会话和宿主工具边界，才能控制研究产物归属；有取消和预算，再增加子代理；最后由 UI 消费同一任务状态。这是便于说明架构的顺序，不是已经核实的个人开发日程。[E01、E03、E07、E10]

验证分成三层。源码检查能证明机制存在；测试定义说明已经准备了哪些断言；实际运行报告才证明特定版本在特定环境通过。仓库文档记载了 2026-09-14 的测试和 Pi SDK 联调，但不能把那天的结果自动推广到当前全部研究功能。本轮只完成源码/测试定义核对和简历材料校验，未运行程序测试或真实 API。[E04、E06、E08、E11、E12]

## M6 · 两个可以讲透的失败场景

### 场景一：父任务取消时，有的子任务正在运行，有的还在排队

不要只回答“调用 AbortController”。真正要回答的是：排队任务是否会继续拿到槽，运行任务是否停止，释放动作是否重复，最终报告是否留下一个永远 running 的状态。当前实现把父取消与子任务截止时间组合，排队等待可取消，运行中的子代理会销毁，finally 中释放槽并保存 cancelled/failed 等终态。对应测试构造运行与排队并存的情况，检查没有额外子任务在取消后继续启动。[E01、E04]

这是已有代码和测试场景，不能包装成“线上某次事故造成损失，我连夜修好了”。演示失败恢复时应展示测试输入与断言。

### 场景二：一个子任务结果不错，但另一个子任务报告写盘失败

这里不能笼统说“失败不影响其他任务”。普通模型调用失败会形成失败报告，父任务还能获得成功兄弟的结果；持久化失败则属于更深一层的错误，委派调用可能最终整体报错。`allSettled` 仍要求先等其他兄弟完成清理，避免错误返回后残留执行工作。测试通过破坏一个报告目的路径注入写失败，并确认兄弟任务已完成清理；本轮只读了测试定义，没有执行它。[E01、E04]

正确的恢复说明是“保留已经落下的产物，明确当前调用失败原因”，不是“所有结果一定成功返回”。

## M7 · 项目边界与后续优先级

**现在可以讲**：研究专用工具及来源产物、宿主工具面、受限 Pi 子代理、Claude 字符预算历史桥接、已有后端配置切换、任务生命周期和流式检查点。

**现在不能讲**：三个后端研究能力完全一致；全自动阶段模型路由；通用多 Agent 调度平台；完整 SDK resume；长期语义记忆；完整研究质量 Benchmark；所有事件可重放；全链路防注入；所有凭据不进入子进程；全量测试在本次全部通过。[E01—E15]

下一阶段应先对齐 Pi 研究路径的历史预算与工具记录回填，并补**当前研究路径的可重复端到端验收记录**，再考虑研究质量评估：给出固定问题、来源、工具轨迹、报告和失败对照，明确模型调用成本与环境。之后再建立小型正例/反例/模糊例集合，测试来源过时、证据冲突和引用不支持结论的情况。这是后续设计，不写进现有简历成果。

## M8 · 展开口述稿与术语速查

### 展开口述稿

> ThreadCove 的场景是个人技术研究，输入通常是一个要比较或调查的问题。这个场景的难点不只是让模型生成答案，而是研究过程中资料从哪里来、哪些子问题可以分开做、执行失败后还剩下什么。
>
> 我把项目分成模型调用和宿主管理两部分。模型可以请求搜索、读取网页，或者把独立子问题委派出去；宿主决定它实际拥有的工具、能用多少资源，以及何时停止。当前研究路径接在 Pi 后端，MCP 代理工具和研究工具都通过宿主执行入口接入。每次取材保存来源和时间，所以后面可以回看依据，但我不会把“有 URL”当成“结论已经验证”。
>
> 子代理部分不是无限开多个模型。我用共享并发槽和每轮预算限制扇出，子代理只拿到叶子研究工具面；父任务取消和子任务超时都会传播，最终要清理进程并留下状态。常规子任务失败可以与成功结果一起返回，写盘失败则必须明确报错，不能因为部分答案生成了就标记整个任务成功。
>
> 上下文也需要单独管理。Claude 适配路径按字符预算取最近的有效历史，保留角色和顺序，并与当前问题分开；Pi 研究路径目前使用另一套 user/assistant 回填，预算和工具历史尚未对齐。我会把这两条路径分开讲，不把局部文本桥接夸大为全后端长期记忆。
>
> 工程层用 AgentBackend 把后端接口统一起来，Pi SDK 放在 JSONL 子进程里；任务层区分请求受理和真正完成，用稳定消息 ID、累计快照和检查点保存进度。重启后能恢复已保存文本并标记中断，不会自动重放付费调用。
>
> 当前项目最有价值的是可检查、可约束的研究执行链。研究质量评估和跨后端工具能力对齐仍需补充，我不会把这些计划当成已经交付的结果。

### 容易混淆的术语

| 术语 | 本项目中的准确含义 |
|---|---|
| Harness | 给模型组织工具、上下文与执行交互的应用层；不是所有执行隔离措施的总称。 |
| Runtime | 本项目实际执行所处的进程、宿主和生命周期边界；不能凭一个接口就称完整 Runtime 平台。 |
| Session / Workspace | Session 管会话与任务记录；Workspace 管所属环境、来源和偏好，可容纳多个 Session。 |
| Source / Tool / Skill | Source 偏连接与配置；Tool 是模型可调用能力；Skill 是使用方式或步骤的指令材料。目录内用于写简历的 Skill 不等于项目运行时新增功能。 |
| delegate_research | 受约束的叶子研究子代理委派，不是通用多 Agent DAG。 |
| 历史恢复 | 宿主保存文本的有限注入；不等同于 provider 原生 session resume。 |
| AgentEvent | 事件形状与消费契约；持久化、重试和回放需要另外实现。 |
| 来源产物 | 带 URL/时间/正文的取材记录；不等同于逐论点验证完成的证据链。 |
| 回归测试 / Agent Eval | 前者可检查预算、取消和字段；后者还要检验任务与研究结论质量，当前不能混为一谈。 |
