# MiniCode 项目面试 Q&A（付费版）

## 使用说明

本文件和 `02-MiniCode简历要点库-付费版.md` 一一对应。简历里写了哪个 `Rxx`，就至少准备对应 `Qxx.x`。

回答时遵循四段式：

1. 这个设计解决什么问题。
2. MiniCode 里大概怎么实现。
3. 为什么不用更简单或更复杂的方案。
4. 这个设计有什么限制或可扩展方向。

## Q01 Agent Loop 执行闭环

### Q01.1 MiniCode 的 Agent Loop 是怎么跑起来的？

MiniCode 的核心是 model-tool-model 闭环。用户输入进入 TUI 后会交给 `runAgentTurn`，Agent Loop 将当前消息历史发送给模型适配器。模型可能返回普通 assistant 文本，也可能返回 `tool_calls`。如果返回工具调用，系统通过 `ToolRegistry` 找到对应工具，执行后把结果作为 `tool_result` 追加回消息历史，再进入下一轮模型推理。直到模型返回最终回答或达到终止条件。

### Q01.2 为什么 Agent 需要多轮工具调用，而不是一次模型请求直接回答？

代码任务需要观察外部环境。模型一开始并不知道文件结构、代码内容、命令输出和修改结果，所以必须通过工具逐步获取信息。多轮循环允许 Agent 先搜索文件、再读取内容、再执行修改、再根据结果继续调整。这就是 Coding Agent 和普通 Chatbot 的核心区别。

### Q01.3 你怎么防止 Agent Loop 无限执行？

MiniCode 通过 `maxSteps` 限制最大步骤数，同时对空响应、thinking stop 等异常分支做重试和回退。模型返回最终 assistant 消息时会终止；工具调用执行后才继续下一轮；不可恢复异常会返回诊断信息而不是继续空转。

## Q02 Agent Turn 状态机与边缘恢复

### Q02.1 progress 消息和 final answer 为什么要区分？

长任务中 Agent 可能需要向用户报告“正在搜索文件”“正在执行测试”等中间状态，这些消息不能终止当前轮次。MiniCode 用 `assistant_progress` 或 progress kind 表示中间状态，普通 assistant 消息才代表最终回答。这样 TUI 可以持续反馈进度，同时 Agent Loop 不会误以为任务完成。

### Q02.2 thinking stop 或空响应怎么处理？

空响应会触发重试，系统会注入继续提示让模型继续输出；如果模型在 thinking 阶段因为 `max_tokens` 或 `pause_turn` 停止，MiniCode 会识别为可恢复停止，并提示模型从中断点继续。如果多次失败，则返回诊断信息，避免无限重试。

### Q02.3 `maxSteps` 到达后 Agent 如何处理未完成的任务？和 timeout 有什么区别？

`maxSteps` 限制的是 Agent 轮次数，防止循环无限执行。到达上限后，当前任务会终止并返回诊断信息，告诉用户已达到最大步骤数。它和 timeout 不同：`maxSteps` 是计数上限，关注的是步骤数量；timeout 关注的是单步或整体执行时间。两者可以共存，分别从不同维度保护系统不被空转耗尽。

## Q03 Model Adapter 抽象

### Q03.1 为什么要做 ModelAdapter，不直接在 Agent Loop 里调 Anthropic？

Agent Loop 关心的是“下一步是什么”，不应该关心不同模型 API 的消息格式、响应结构和错误处理。ModelAdapter 把 provider 细节封装起来，对外只返回统一的 `AgentStep`。这样后续换模型、做 Mock 测试或兼容新响应格式时，不需要改核心循环。

### Q03.2 MockModelAdapter 的价值是什么？

MockModelAdapter 可以让测试不依赖真实 LLM API。Agent Loop、工具调度、异常恢复等逻辑可以用确定性输入输出测试，避免因为网络、模型随机性或 API 成本导致测试不稳定。

## Q04 系统提示词构建

### Q04.1 MiniCode 的系统提示词里应该包含什么？

除了基础行为指令，还要包含当前权限上下文、可用 Skills、MCP 服务器状态、记忆/指令文件和响应协议。对 Agent 来说，系统提示词是能力边界说明：它告诉模型有哪些工具可用、哪些操作受限、应该如何返回进度和最终答案。

### Q04.2 为什么 Skills 和 MCP 状态要进入系统提示词？

模型只有知道这些能力存在，才可能选择调用它们。MiniCode 采用渐进方式：系统提示词提供技能摘要和 MCP 状态，真正需要时再加载完整 Skill 或执行 MCP 工具。这样既能让模型感知能力，又不把大量上下文一次性塞进去。

## Q05 Token 估算与上下文监控

### Q05.1 为什么要做 token 估算？

Agent 长会话会不断追加用户消息、工具调用、工具结果和摘要，如果不监控上下文使用量，很容易超过模型窗口。MiniCode 通过 provider usage 和本地启发式估算结合，计算当前利用率，并把状态分为 normal、warning、critical、blocked，驱动后续压缩策略。

### Q05.2 为什么不只依赖 provider 返回的 token usage？

provider usage 通常只覆盖已经发生过的 API 请求，而当前会话尾部新增的消息可能还没被 provider 计入。MiniCode 使用“最新准确计数 + 后续消息估算”的方式，兼顾准确性和实时性。

## Q06 分层上下文压缩

### Q06.1 MiniCode 为什么要做多层压缩？  

不同上下文压力需要不同处理。轻微膨胀时只清理旧工具结果即可；接近上限时需要折叠或剪裁历史；严重超限时才用模型摘要。多层压缩能避免一上来就做昂贵或有信息损失的自动摘要。

### Q06.2 microcompact、context collapse、snip compact、auto compact 有什么区别？

microcompact 主要清理旧工具结果；context collapse 是给模型看的投影视图，保留原始转录本；snip compact 会硬删除部分非受保护消息；auto compact 使用模型生成摘要替换旧历史。它们的触发时机和信息损失程度不同。

### Q06.3 为什么不能简单把前面的消息全部删掉？

Agent 任务中很多关键状态来自历史，比如已经修改过哪些文件、工具调用是否成功、错误原因是什么。简单删除会导致模型失去任务连续性。MiniCode 会尽量保护关键工具调用、最近消息和编辑相关上下文。

## Q07 大型工具结果外置化

### Q07.1 大型工具结果为什么危险？

例如读取大文件、搜索大量结果或命令输出很长时，工具结果会迅速占满上下文窗口。模型真正需要的往往只是摘要、预览或后续按需读取的路径，而不是把所有原始输出都塞进 prompt。

### Q07.2 外置化和截断有什么区别？

截断会直接丢失信息；外置化是把完整结果保存到本地文件或存储区域，在上下文里放预览和指针。这样模型上下文变小，但系统仍然保留审计和回溯能力。

### Q07.3 外置化存储的生命周期怎么管理？用户想回溯完整结果怎么办？

外置化结果保存在会话关联的本地存储中，随会话生命周期存在。用户可以通过工具输出中的指针路径随时查看完整内容，不依赖模型上下文的记忆。当会话被清理或过期时，外置化结果一并清理。这不是长期记忆系统，而是当前会话内的上下文置换策略。

## Q08 ToolDefinition 与 ToolRegistry

### Q08.1 ToolDefinition 为什么要同时有 JSON Schema 和 Zod schema？

JSON Schema 用来告诉模型应该生成什么参数；Zod schema 用来在运行时校验模型实际传来的参数。一个面向模型生成，一个面向程序安全执行。两者结合可以降低工具调用输入不合法的风险。

### Q08.2 ToolRegistry 解决什么问题？

ToolRegistry 统一管理工具注册、查找、执行和资源清理。Agent Loop 不需要知道每个工具的具体实现，只要按名称查找并执行即可。它还方便把内置工具、MCP 工具和 Skill 相关工具放到同一套调度体系里。

## Q09 内置文件与搜索工具

### Q09.1 Agent 为什么需要 `list_files`、`read_file`、`grep_files`？

Coding Agent 必须先观察代码库。`list_files` 帮它理解目录结构，`grep_files` 帮它定位符号或文本，`read_file` 帮它读取具体上下文。没有这些工具，模型只能凭用户描述猜代码。

### Q09.2 为什么 `read_file` 要做分页和最大长度限制？

源文件可能很大，直接读取全部内容会浪费上下文甚至导致超限。分页和限制让 Agent 可以先读关键片段，再按需继续读取，同时工具输出中会提供 total、offset、truncated 等元信息指导下一步。

## Q10 写入前审查与 Diff 流程

### Q10.1 写入前审查的完整流程是什么？

文件修改工具不会直接写盘，而是先计算旧内容和新内容的 unified diff，再调用 `PermissionManager.ensureEdit` 请求用户审批。用户确认后才创建目录并写入文件。如果内容没有变化，则直接返回成功，避免无意义审批。

### Q10.2 为什么 diff 审查比“确认是否写入”更好？

因为用户需要知道 Agent 到底改了什么。单纯问“是否允许写入”信息不足；diff 能展示新增、删除和上下文行，让用户在批准前判断是否安全和正确。

## Q11 Shell 执行与后台任务

### Q11.1 MiniCode 怎么判断一个命令是否需要权限？

它会先规范化命令输入，再判断是否是只读命令、开发命令、未知命令或 Shell 片段。只读命令风险较低，开发命令和未知命令更可能触发权限检查。包含管道、重定向、变量等 Shell 片段时，因为静态分析困难，也会更谨慎。

### Q11.2 后台任务是怎么处理的？

如果命令以后台方式运行，系统会 spawn 子进程并注册后台任务记录，保存 PID、命令和状态。后续通过检查进程是否仍存在来刷新 running、completed 等状态，适合开发服务器这类长时间运行命令。

## Q12 PermissionManager 权限系统

### Q12.1 PermissionManager 管哪三类权限？

它主要管路径访问、命令执行和文件编辑。路径访问防止越界读取或写入；命令执行防止危险 Shell 操作；文件编辑接入写入前审查，确保修改经过用户确认。

### Q12.2 allow_once、allow_turn、allow_always 有什么区别？

`allow_once` 只允许当前这一次；`allow_turn` 允许当前 Agent 轮次内相关操作；`allow_always` 会持久化，以后类似操作不再重复询问。作用域不同，便利性和风险也不同。

### Q12.3 deny_with_feedback 有什么价值？

它不仅拒绝操作，还能把原因反馈给模型。这样 Agent 可以根据用户给出的理由调整方案，而不是只收到一个失败信号。

## Q13 MCP Host 集成

### Q13.1 MCP 在 MiniCode 里扮演什么角色？

MiniCode 作为 MCP host，可以连接外部 MCP server，把外部工具、资源和提示包装成内部 ToolDefinition。这样 Agent 不只会用内置文件和 Shell 工具，也能动态接入专业服务。

### Q13.2 为什么 MCP 工具名要用 `mcp__server__tool`？

这是命名隔离。不同服务器可能有同名工具，外部工具也可能和内置工具重名。加上服务器名后，工具名称更稳定，也能避免冲突。

## Q14 MCP 配置、Token 与协议缓存

### Q14.1 为什么 MCP token 要单独存储？

项目级 `.mcp.json` 可能进入版本控制，如果把 token 放进去会泄露凭据。MiniCode 把远程服务器 token 存在单独的 `mcp-tokens.json`，配置和密钥分离，更适合真实开发环境。

### Q14.2 协议缓存解决什么问题？

不同 MCP server 可能使用 content-length、newline-json 或 streamable-http 等不同协议帧格式。首次连接时探测协议，成功后缓存偏好，后续连接就不需要重复探测，初始化更快也更稳定。

## Q15 Skills 渐进式加载系统

### Q15.1 Skills 和 MCP 的区别是什么？

MCP 更像可执行工具协议，提供外部函数、资源和提示；Skills 更像 Markdown 工作流和领域知识，用 `SKILL.md` 指导模型怎么做某类任务。一个偏工具能力，一个偏过程知识。

### Q15.2 为什么不把所有 Skill 全部放进系统提示词？

Skill 全文可能很长，而且大多数任务只需要其中一小部分。MiniCode 先暴露名称和描述，让模型知道有哪些技能；真正相关时再调用 `load_skill` 加载完整内容。这是典型的渐进式上下文加载。

## Q16 TUI 全屏交互与 ScreenState

### Q16.1 TUI 为什么需要 ScreenState？

终端 UI 不是简单打印文本，它要同时维护输入框、滚动历史、活跃工具、上下文统计、权限弹窗和忙闲状态。`ScreenState` 把这些状态统一管理，每次状态变化后重新渲染屏幕。

### Q16.2 权限弹窗如何阻塞 Agent？

当权限系统请求用户审批时，TUI 会设置 `pendingApproval`，输入焦点转到审批界面。Agent Loop 会等待用户选择允许或拒绝，审批结果返回后工具执行才继续。

## Q17 Slash Commands 与本地工具快捷方式

### Q17.1 为什么要提供 `/read`、`/grep` 这种本地快捷方式？

有些操作是确定性的，不需要 LLM 推理。例如直接读文件、列目录、搜索文本。快捷方式可以绕过模型，降低延迟和 token 成本，也给高级用户更强控制感。

### Q17.2 这些快捷方式和 Agent 工具是什么关系？

它们最终映射到同一套内置工具，比如 `/read` 映射到 `read_file`，`/grep` 映射到 `grep_files`。区别只是调用入口不同：一个来自用户显式命令，一个来自模型 tool call。

## Q18 会话持久化、恢复与分支

### Q18.1 为什么会话用 JSONL 存储？

JSONL 是追加友好的。每条消息、工具调用或边界标记都是一行事件，写入简单，崩溃时也更容易保留已写入历史。它适合长时间运行的 Agent 会话审计和恢复。

### Q18.2 `/fork` 的意义是什么？

Fork 允许用户从当前上下文分支出一个新会话，尝试不同方案，同时不破坏原始会话。它通过 parentUuid 或 logicalParentUuid 维持分支关系，让历史可以被重建。

## Q19 多层配置系统

### Q19.1 MiniCode 的配置优先级是什么？

大体是从低到高：Claude 设置、全局 MiniCode MCP、项目 MCP、MiniCode 用户设置、环境变量。环境变量通常最高，因为它适合运行时临时覆盖模型、API 地址和 token。

### Q19.2 `loadEffectiveSettings` 和 `loadRuntimeConfig` 有什么区别？

`loadEffectiveSettings` 负责合并配置文件，得到文件层面的有效设置；`loadRuntimeConfig` 在此基础上叠加环境变量和默认值，生成 Agent 实际运行时使用的配置。

## Q20 Web Search / Web Fetch 工具

### Q20.1 为什么搜索和抓取要拆成两个工具？

搜索负责发现候选 URL，抓取负责读取具体页面内容。拆开后 Agent 可以先判断哪些结果值得打开，避免一次性抓取大量无关页面。

### Q20.2 Web Fetch 为什么要做可读性提取和截断？

网页包含大量导航、脚本、广告和无关结构。可读性提取能保留正文，截断能控制上下文大小。这样 Agent 获取外部信息时不会把 prompt 塞满。

## Q21 响应协议与进度消息

### Q21.1 进度消息对用户体验有什么价值？

Agent 执行长任务时，如果界面长时间没有反馈，用户会以为卡住了。progress 消息可以展示当前阶段，比如正在搜索、正在运行测试、正在等待工具结果，让用户知道任务仍在推进。

### Q21.2 为什么不能把所有 assistant 文本都当最终回答？

因为中间状态不代表任务完成。如果误终止，后续工具执行和总结就不会发生。MiniCode 用协议区分中间 progress 和最终 answer，保证循环语义清晰。

## Q22 轻量可追溯的 Claude Code 参考实现

### Q22.1 MiniCode 和 Claude Code 的关系应该怎么讲？

稳妥说法是“参考 Claude Code 类产品的核心交互模式，实现一个轻量级、可学习、可追溯的 Coding Agent 原型”。不要说“复刻 Claude Code”或“具备完整 Claude Code 能力”。

### Q22.2 这个项目为什么适合写简历？

因为它覆盖了 Agent 项目的关键工程问题：工具调用、上下文治理、权限安全、会话持久化、扩展机制和终端交互。它不是只调一个 LLM API，而是有完整的本地开发工作流闭环。
